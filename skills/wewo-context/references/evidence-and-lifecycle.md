# Evidence by operation

Select evidence according to the claim being synchronized. No operation needs
all six development capabilities to have run or every possible report to exist.
File existence, a final-looking heading, or an approved proposal alone never
proves implementation completion.

## Initialize

Selectively inspect current code and authorized confirmed sources. A first
requirement may have no older documents; an existing project may have selected
completed requirements worth consulting. Do not scan all prior workspaces.

Establish a known common baseline and applicability before presenting facts as
project-wide. If only branch evidence is available, propose a branch snapshot
or clarify the common baseline; do not silently expand a branch-only request
to both context files. Initialization and confirmed non-code policies need no
invented test or review evidence. Qualify what code inspection alone establishes.

## Synchronize a selected completed requirement

Compare the selected requirement/design, when available, with relevant current
code and applicable implementation/verification evidence. Available records,
test results, and reviews can help; team-provided equivalent evidence from work
outside this plugin is equally eligible. Inspect what the evidence proves,
its scope, revision, and relevance to the actual implementation.

For each candidate conclusion, distinguish:

- completion supported for this behavior and actual revision;
- confirmed policy whose enforcement is incomplete;
- incomplete, contradicted, or unverified implementation;
- stale evidence for an earlier or different implementation.

Only the first category supports a completed implementation fact. The second
can be retained as policy with its enforcement gap. Explain the affected
omission or conflict for the others; do not infer the intended requirement from
code that contradicts a confirmed rule. Supported independent facts may still
be synchronized without unrelated reports or a blanket completion claim.

An existing context claim is reusable only within its scope and provenance.
When current evidence contradicts it, prepare an explicit correction or
removal supported by evidence and include that in the confirmed change set.
Do not silently treat a stale report as fresh verification or claim to have
executed tests merely because their output was supplied.

## Promote project context

Identify the shared or integration baseline and intended common applicability;
do not assume its name is `main` or `master`. Prefer promotion after the change
has reached that baseline. Inspect accessible local baseline evidence and use
user-provided confirmation for facts unavailable locally, qualifying the limits.
No GitHub/GitLab API is required.

"Present on this branch" and "ready to merge" do not prove common availability.
If evidence only supports the branch, explain why the common fact cannot yet
be established. If explicitly asked to prepare a pre-merge amendment, label
its proposed integration baseline and pending status visibly; it must not read
as established common behavior. Do not perform Git operations as a consequence.

Promotion can update the project file alone. Updating branch context to remove
a now-covered duplicate is a separate part of the proposed per-file change set;
do it only within confirmed scope and after verifying that the applicable fact
is present in this checkout's project context. Concurrent edits or a failed
project write must not cause the only available branch fact to be removed.

## Evidence-sensitive stopping

Stop the affected claim when a material conflict, missing baseline, or missing
authorization prevents a truthful conclusion. Present the supported patch and
the remaining uncertainty separately. A no-op or partial supported update is
preferable to inventing completion, but do not call an incomplete requested
update complete. Apply only the concrete confirmed scope, then verify actual
file contents and referenced evidence as directed in the entrypoint.
