# `wewo-testplan` Skill 需求说明

## 1. Skill 定位

`/wewo-testplan` 是 `wewo-skills` 中负责测试设计的 Skill。

它用于在代码实现前，根据当前可用的需求材料、技术设计、项目代码和已有测试资料，提前制定测试计划并生成详细测试用例。

本 Skill 不负责执行测试，也不负责决定具体测试工具、自动化可行性或执行阶段。

它需要回答两个核心问题：

1. 本次需求整体应该怎么测试；
2. 具体需要验证哪些测试场景。

最终生成两个文件：

```text
test-plan.md
test-cases.md
```

其中：

```text
test-plan.md
→ 测试范围、风险、策略、覆盖条件与测试数据假设

test-cases.md
→ 具体测试用例、测试层级和证据层级
```

## 2. Skill 独立性

`/wewo-testplan` 可以独立运行，不依赖其他能力已经执行。

用户可以在以下场景中直接使用：

- 已经拥有完整 PRD；
- 已经拥有技术设计文档；
- 只有一段较明确的需求描述；
- 只有页面截图、原型图或接口文档；
- 已经存在项目代码；
- 已经存在测试人员编写的测试点；
- 希望复用用户显式提供的 `prd.md` 或 `technical-design.md`；
- 希望直接为已有功能补充测试计划和测试用例。

仅当用户在当前交互中显式提供、显式引用，或已确认的对话上下文中存在时，才应将其作为可用输入之一。不得自动扫描 `docs/wewo/` 或仓库寻找历史工作流文档；文档存在于工作区本身不构成读取授权。

如果以下文件由用户显式提供或在当前对话上下文中存在，可以将其作为可用输入之一：

```text
prd.md
technical-design.md
```

但不得因为这些文件不存在而拒绝执行。

不同 Skill 之间保持松耦合：

```text
可以独立使用；
也可以连续使用；
存在且被用户显式提供或已在对话中确认的工件时进行复用；
不存在可用工件时仍能正常工作。
```

## 3. 可接受的输入

`/wewo-testplan` 可以综合分析以下材料：

- 用户当前输入的需求描述；
- 当前对话中的需求信息；
- PRD 或其他需求文档；
- `prd.md`；
- 技术设计文档；
- `technical-design.md`；
- Markdown、TXT、Word、Excel、PPT、PDF 等文件；
- 页面截图、原型图或流程图；
- API 文档；
- Issue、任务单、变更说明或缺陷描述；
- 当前项目代码；
- 历史缺陷；
- 多份相互关联的材料。

Skill 应综合使用当前能够获得的材料，不应默认某一个文件是唯一事实来源。

上述输入仅在用户当前交互中显式提供、显式引用，或已确认的对话上下文中存在时才可使用；不得自动扫描工作区或仓库发现历史文档。

如果多份材料之间存在冲突，应明确指出冲突，并通过多轮对话让用户确认最终测试依据。

## 4. 核心目标

`/wewo-testplan` 需要完成以下工作：

1. 收集并理解当前可用的需求、设计和测试材料；
2. 判断当前信息是否足以进行测试设计；
3. 理解本次测试对象、业务规则和影响范围；
4. 识别测试设计所需的覆盖条件与测试数据假设；
5. 识别核心业务风险、异常场景和回归风险；
6. 为不同风险选择合适的测试层级；
7. 通过必要的多轮对话确认测试范围、覆盖条件与测试数据假设；
8. 制定整体测试计划；
9. 生成详细、可执行、可判断结果的测试用例；
10. 对生成的测试用例进行一次内部评审；
11. 生成 `test-plan.md` 和 `test-cases.md`。

完整流程为：

```text
收集需求、设计、代码和测试材料
    ↓
分析测试对象与信息充分性
    ↓
识别业务规则与质量风险
    ↓
识别覆盖条件与测试数据假设
    ↓
确认测试范围、覆盖条件与测试数据假设
    ↓
制定测试策略
    ↓
生成详细测试用例
    ↓
标记测试层级和证据层级
    ↓
执行测试用例自评审
    ↓
用户确认
    ↓
生成 test-plan.md
生成 test-cases.md
```

## 5. 测试设计应在代码实现前完成

本 Skill 的主要使用时机是代码实现之前。

测试计划和测试用例应尽量提前生成，为开发人员、测试人员和后续验证提供共同依据。

需要区分以下三种内容。

### 5.1 测试计划

回答：

> 本次需求整体准备怎么测试？

包括：

- 测试目标；
- 测试范围；
- 质量风险；
- 测试层级；
- 覆盖条件与测试数据假设；
- 测试数据；
- 验证方式与证据要求；
- 准入和退出条件。

### 5.2 测试用例

回答：

> 具体需要验证哪些场景？

包括：

- 前置条件；
- 测试数据；
- 操作步骤；
- 预期结果；
- 优先级；
- 推荐测试层级；
- 必需证据层级（仅当业务风险或可观察行为要求时）。

### 5.3 自动化测试代码

回答：

> 如何使用具体测试工具执行测试用例？

例如：

- 单元测试函数；
- 集成测试代码；
- 接口测试脚本；
- 页面自动化脚本；
- Fixture；
- Mock；
- 页面选择器；
- 测试数据准备脚本。

这部分不属于 `/wewo-testplan` 的主要职责。

自动化测试代码、具体测试工具选择以及自动化可行性判断不属于测试设计职责。

## 6. 不定义 TDD 或自动化契约

`/wewo-testplan` 不定义测试驱动开发（TDD）契约，也不决定测试用例最终是否自动化或使用何种具体测试工具。

测试用例通过「推荐测试层级」和「必需证据层级」描述场景需要哪种直接证据。例如「推荐测试层级：E2E；必需证据层级：E2E」表达该场景需要端到端证据，但不决定具体工具，也不决定该场景最终是否自动化。

测试设计不决定具体测试实现方式、工具选择或自动化可行性。

## 7. 需求与测试信息充分性判断

进入详细测试设计前，Skill 应判断当前信息是否足够。

至少需要理解：

- 本次要测试什么；
- 核心用户或角色；
- 核心业务流程；
- 关键业务规则；
- 允许和禁止的状态；
- 主要异常和边界；
- 本次测试范围；
- 预期业务结果。

如果信息已经足够，应直接进行测试设计，不要重复进行完整需求访谈。

如果只缺少少量信息，应在当前阶段直接询问，例如：

- 哪些角色需要覆盖；
- 是否可以创建和删除测试数据；
- 是否可以 Mock 第三方服务；
- 是否存在验证码、短信或第三方登录；
- 需要支持哪些平台、浏览器或终端（作为需求的覆盖范围）；
- 哪些已有功能属于回归范围；
- 是否允许执行破坏性测试；
- 当前最关注哪些高风险场景。

如果需求过于模糊，无法判断测试目标和预期结果，应先继续澄清，不得直接生成大量猜测性测试用例。

只有当用户希望完整重新梳理产品需求时，可以请求额外的需求澄清或需求上下文，但不能将其作为强制前置条件。

## 8. 多轮对话机制

`/wewo-testplan` 应采用必要的多轮对话，但不能将流程变成长篇测试问卷。

每轮围绕一个测试主题，通常询问 1～3 个紧密相关的问题。

可以根据实际需求依次讨论：

1. 测试对象和范围；
2. 核心业务风险；
3. 用户角色与权限；
4. 覆盖条件与测试数据假设；
5. 测试数据；
6. 外部服务和 Mock；
7. 支持的平台、浏览器或终端覆盖范围；
8. 回归范围；
9. 验证方式与证据要求。

用户每次回答后，应重新判断：

- 哪些测试条件已经明确；
- 当前回答是否产生新的风险；
- 哪些问题仍会影响测试用例；
- 是否已经具备生成最终文档的条件。

## 9. 问题应附带 AI 的判断和建议

不能只问：

```text
这次需要测什么？
```

每个问题应尽量包含：

- 根据当前材料发现了什么；
- 当前存在什么测试风险；
- AI 推荐采用什么测试方式；
- 为什么推荐这种方式；
- 需要用户确认的具体内容。

推荐格式：

```markdown
### 当前测试主题

根据需求、技术设计和现有项目，我目前理解为：

……

主要风险是：

……

我的建议是：

……

需要确认：

1. ……
2. ……
```

示例：

```markdown
### 当前测试主题：订单取消的测试层级

根据当前需求，订单取消同时涉及状态规则、权限和库存回退。

我的建议是：

- 状态规则和权限判断使用单元测试；
- 订单状态与库存一致性使用集成测试；
- 用户从订单详情页完成取消使用浏览器 E2E；
- 重复取消优先通过单元和集成测试验证，不需要创建多条重复 E2E。

需要确认：

1. 测试数据是否允许创建、清理或复用？
2. 是否可以稳定准备待发货订单的测试数据？
```

## 10. 测试用例不能机械生成

不能简单地把需求文档中的每一句话转换成一条测试用例。

生成前应先完成：

```text
测试视角需求分析
→ 风险分析
→ 测试策略
→ 测试用例设计
→ 测试用例评审
```

不能生成以下低质量用例：

```text
操作与该需求相关的功能；
观察页面和接口；
结果应符合需求。
```

每条用例必须：

- 有明确测试目标；
- 有可满足的前置条件；
- 有具体测试数据；
- 有清晰操作步骤；
- 有可以判断通过或失败的预期结果；
- 与实际业务规则相关；
- 不把未决问题当成已确定测试用例。

## 11. 测试设计方法

Skill 应根据需求特征，主动选择合适的测试设计方法，而不是只笼统地生成正常、异常和边界用例。

可选方法包括：

- 等价类划分；
- 边界值分析；
- 决策表；
- 状态迁移；
- 场景法；
- 因果关系分析；
- 错误推测；
- 权限矩阵；
- 数据组合；
- 成对组合；
- 并发与幂等分析；
- 风险驱动测试；
- 历史缺陷回归。

示例：

```text
数量限制
→ 使用边界值分析

不同角色和资源归属
→ 使用权限矩阵

多种条件共同决定结果
→ 使用决策表

订单状态变化
→ 使用状态迁移

完整用户操作
→ 使用场景法
```

Skill 应在测试计划中说明本次采用了哪些测试设计方法。

## 12. 测试层级选择

不能要求每个测试场景同时生成单元、集成、接口和 E2E 测试。

应选择最合适、成本最低且能够有效发现问题的测试层级。

可选层级包括：

- 单元测试；
- 组件测试；
- 接口测试；
- 集成测试；
- 契约测试；
- E2E 测试；
- 安全行为测试；
- 数据与迁移测试；
- 性能与稳定性测试；
- 人工测试。

示例：

```text
纯业务规则
→ 优先单元测试

数据库事务
→ 优先集成测试

接口参数和权限
→ 优先接口或集成测试

完整用户关键流程
→ E2E

视觉效果和主观体验
→ 人工测试
```

测试用例中必须标记推荐测试层级。

## 13. 测试风险分析

Skill 应从测试视角主动识别风险，而不是只覆盖需求中明确写出的正常流程。

根据当前需求动态考虑：

### 13.1 正常流程

- 核心用户路径；
- 主要功能结果；
- 正常状态流转；
- 正常数据处理。

### 13.2 异常与边界

- 空值；
- 非法值；
- 最小值和最大值；
- 超出范围；
- 数据不存在；
- 状态已变化；
- 操作中断；
- 外部依赖失败。

### 13.3 权限与安全

- 未登录；
- 不同角色；
- 资源归属；
- 横向越权；
- 纵向越权；
- 敏感数据；
- 输入校验；
- 文件上传和下载；
- 业务规则绕过；
- 批量操作。

### 13.4 可靠性与业务正确性

- 重复提交；
- 并发修改；
- 幂等；
- 事务；
- 部分成功；
- 状态冲突；
- 重试；
- 消息重复消费；
- 缓存不一致；
- 定时任务重复执行。

### 13.5 回归风险

- 受影响的已有页面；
- 受影响的已有接口；
- 公共模块；
- 状态流程；
- 数据结构；
- 兼容性；
- 旧客户端或旧数据。

## 14. 不做自动化可行性判断

`/wewo-testplan` 不检查、选择、配置或推断具体测试工具、测试运行器、浏览器安装或执行基础设施，除非用户显式提出需要针对具体工具进行测试设计。它不判断每条测试用例是否适合自动化，不安装包、不修改依赖清单或 Lock 文件、不配置测试运行器。

测试用例通过「推荐测试层级」和「必需证据层级」表达场景需要何种直接证据，例如 Unit、Integration、API、E2E、Manual 等。

测试设计不依赖项目现有测试工具或执行环境，也不仅为了测试计划引入新的工具。

## 15. Web E2E 作为测试层级

Web E2E 是测试层级之一，只应用于少数关键端到端用户旅程，且该层级能提供更直接的证据时才推荐。不应默认所有功能测试都需要浏览器 E2E。

`/wewo-testplan` 不判断某条用例是否适合浏览器自动化，不选择或检查具体浏览器自动化工具，不检查浏览器可用性，不询问浏览器或测试运行器的安装。测试设计不选择或推断浏览器 E2E 的具体工具、安装或执行。

## 16. 测试用例优先级

测试用例优先级必须根据业务风险决定，不能简单根据生成顺序分配。

建议使用：

### P0

包括：

- 核心业务流程；
- 权限；
- 资金；
- 库存；
- 关键数据一致性；
- 会阻塞发布的问题；
- 严重安全风险。

### P1

包括：

- 主要异常流程；
- 重要边界；
- 高频操作；
- 重要回归；
- 较高业务影响问题。

### P2

包括：

- 低频场景；
- 一般兼容性；
- 非核心体验；
- 不影响主流程的问题。

## 17. 测试用例自评审

测试用例生成完成后，Skill 必须执行一次内部评审。

评审至少检查：

- 是否覆盖核心需求；
- 是否覆盖高风险业务规则；
- 是否覆盖正常、异常和边界；
- 是否覆盖权限和安全风险；
- 是否覆盖数据一致性；
- 是否存在重复用例；
- 测试层级是否合理；
- 是否将过多场景放入 E2E；
- 前置条件是否可以满足；
- 操作步骤是否具体；
- 预期结果是否可以判断；
- 是否将未知需求写成了确定预期；
- 是否遗漏关键回归范围。

评审结果应写入 `test-cases.md`。

## 18. 对话结束条件

以下情况不应生成最终测试计划和测试用例：

- 基本测试对象仍不明确；
- 核心业务规则存在冲突；
- 关键预期结果尚未确定；
- 用户角色和权限会影响结果但尚未确认；
- 测试范围仍然模糊；
- 会直接改变测试用例的关键环境条件尚未确认；
- 多份材料之间存在关键冲突；
- 用户尚未确认最终测试设计。

主要问题确认完成后，应先总结：

- 测试对象；
- 测试范围；
- 核心质量风险；
- 计划采用的测试层级；
- 验证方式与证据要求；
- 主要环境或数据限制；
- 未决问题。

然后询问用户：

```text
以上是否准确表达了本次需求的测试设计？

如果有不准确、遗漏或需要调整的地方，请直接指出。
确认后我将生成 test-plan.md 和 test-cases.md。
```

只有用户确认后，才生成最终文件。

# `test-plan.md` 结构

## 19. 固定核心结构

```markdown
# 测试计划

## 1. 测试概述

## 2. 测试依据

## 3. 测试对象与需求理解

## 4. 测试范围

## 5. 质量风险分析
```

# `test-cases.md` 结构

## 22. 固定核心结构

```markdown
# 测试用例

## 1. 文档说明

## 2. 测试用例概览

## 3. 需求覆盖关系

## 4. 详细测试用例

## 5. 人工测试清单

## 6. 用例评审结果

## 7. 未决问题与阻塞项
```

## 23. 测试用例分组

详细测试用例可以根据需求动态分组，例如：

- 正常业务流程；
- 状态与业务规则；
- 异常场景；
- 边界条件；
- 权限与安全；
- 数据一致性；
- 接口；
- 前端交互；
- 集成；
- E2E；
- 回归；
- 性能；
- 兼容性；
- 人工探索。

只生成当前需求涉及的分组。

## 24. 单条测试用例模板

每条测试用例应使用以下结构：

```markdown
### TC-001 用例名称

- **关联需求**：
- **测试目标**：
- **优先级**：P0 / P1 / P2
- **测试类别**：
- **推荐测试层级**：单元 / 组件 / 接口 / 集成 / 契约 / E2E / 安全行为 / 数据迁移 / 性能可靠性 / 人工
- **必需证据层级**：具体层级或"该层级或更高"（仅在业务风险或可观察行为要求时填写）
- **前置条件**：
- **测试数据**：
- **操作步骤**：
  1.
  2.
- **预期结果**：
  1.
  2.
- **风险或备注**：
```

测试设计阶段不应包含：

```text
实际结果
通过或失败状态
执行时间
缺陷编号
```

这些内容属于执行验证阶段的记录，不写入测试设计文档。

### 推荐测试层级与必需证据层级

- **推荐测试层级（Recommended Test Level）** 是建议性的，可以在提供等效直接证据的前提下调整。
- **必需证据层级（Required Evidence Level）** 是指为验证该场景，可视为充分的证据最低层级，可以是具体层级或"该层级或更高"。它只描述证据要求。

示例：

- 纯格式化逻辑：推荐 Unit；必需 Unit 或更高。
- 跨页面关键浏览器旅程：推荐 E2E；必需 E2E。
- 主观视觉质量：推荐人工；必需人工。

不要为了让每个场景都有"必需证据层级"而给所有场景都要求 E2E。只有业务风险或可观察行为确实要求该层级时，才设置必需证据层级。

## 25. 测试用例概览

建议使用：

```markdown
| 测试层级 | 用例数量 | P0 | P1 | P2 | 必需证据层级 |
|---|---:|---:|---:|---:|---:|
```

所有数字必须根据实际生成的测试用例统计，不能编造。

## 26. 需求覆盖关系

如果需求材料已有编号，应建立追踪关系：

```markdown
| 需求或规则 | 对应测试用例 | 覆盖情况 |
|---|---|---|
```

如果需求没有正式编号，可以使用业务规则简短描述，不要求为了形式创建复杂编号体系。

## 27. 人工测试清单

汇总「推荐测试层级」或「必需证据层级」为人工的用例，作为可执行人工验证任务的索引：

```markdown
| 用例编号 | 用例名称 | 优先级 | 主要验证内容 |
|---|---|---|---|
```

该清单仅用于快速定位，不替代详细测试用例。

## 28. 用例评审结果

应记录：

- 核心需求覆盖情况；
- 高风险场景覆盖情况；
- 重复或可合并用例；
- 当前无法设计的用例；
- 测试层级是否合理；
- 推荐测试层级是否合理；
- 必需证据层级是否合理；
- 仍需补充的内容。

## 29. 输出要求

最终生成：

```text
test-plan.md
test-cases.md
```

运行前不需要存在 `prd.md` 或 `technical-design.md`。

如果不存在可用工件：

- 不创建空文件；
- 不要求用户补齐文档；
- 不阻止本 Skill 继续执行。

生成完成后，应向用户说明：

- 两个文件的生成位置；
- 测试范围和主要风险；
- 各测试层级的用例数量；
- 人工验证用例数量；
- 是否存在阻塞项或未决问题。

不要自动执行测试，也不要自动开始代码实现。

## 30. 文档质量要求

最终测试计划和测试用例必须满足：

- 与当前需求和设计一致；
- 基于实际提供的材料和项目内容；
- 不编造页面、接口、角色、状态或覆盖条件；
- 不将未知规则写成确定预期；
- 测试用例步骤具体；
- 预期结果可以明确判断；
- 优先级基于风险；
- 测试层级选择合理；
- 不重复生成大量相同用例；
- 不把所有场景都堆到 E2E；
- 覆盖正常、异常、边界和高风险场景；
- 明确回归测试范围；
- 生成后完成一次自评审。

## 31. `/wewo-testplan` 不负责的内容

本 Skill 不负责：

- 编写业务实现代码；
- 执行测试驱动开发循环；
- 生成最终可执行测试代码；
- 启动项目；
- 执行测试；
- 修改数据库；
- 生成测试执行报告；
- 判断测试实际通过或失败；
- 自动进入其他能力负责的工作。

`/wewo-testplan` 的唯一职责是：

> 综合当前可用的需求、技术设计、项目代码和测试资料，通过必要的多轮对话进行风险驱动的测试设计，生成完整的测试计划和详细测试用例，通过「推荐测试层级」和「必需证据层级」明确每个场景需要的直接证据，作为验证工作的依据。
