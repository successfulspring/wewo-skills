# `wewo-review` Skill 需求说明

## 1. Skill 定位

`/wewo-review` 是 `wewo-skills` 中负责**独立代码审查和安全审查**的 Skill。

它不负责继续实现功能，而是基于真实代码变更，判断：

- 是否完整实现需求；
- 是否符合技术设计和明确约束；
- 是否符合仓库规范及现有架构；
- 是否存在逻辑、边界、异常和兼容性问题；
- 实际测试是否有效；
- 是否存在认证授权、注入、敏感数据、事务、并发、幂等和供应链风险；
- 当前变更是否具备合并或发布条件。

核心职责可以概括为：

```text
确定审查范围
→ 分析实际 Diff
→ 收集需求、设计和仓库规范
→ 建立变更规模与攻击面基线
→ 使用独立子 Agent 分维度审查
→ 运行项目原生工具及可选专项工具
→ 对候选问题进行复核、归因和去重
→ 计算量化指标
→ 输出代码审查和安全审查结论
```

------

## 2. Skill 独立性

`/wewo-review` 可以独立运行，不强制要求用户先执行：

```text
/wewo-prd
/wewo-erd
/wewo-testplan
/wewo-build
```

它可以审查：

- 当前工作区的未提交修改；
- Staged 修改；
- 最近一次 Commit；
- 指定 Commit；
- 两个 Commit 或分支之间的 Diff；
- 当前功能分支相对于目标分支的 Diff；
- Merge Request 对应的代码；
- 用户指定的文件或目录。

仅当用户明确提供、引用或确认上游文档时（显式提供工作区、显式引用文档、或要求审查某个已有需求），才将其作为审查依据；不得自动扫描 `docs/wewo/` 或仓库寻找历史工作流文档。不存在被授权的上游文档时，仍然可以完成工程质量、安全和可靠性审查。

------

## 3. 产出文档

固定生成两个文档：

```text
07-code-review.md
08-security-review.md
```

其中：

```text
07-code-review.md
→ 需求符合性、设计符合性、代码正确性、代码结构、
  测试质量、影响兼容性、量化指标和合并结论

08-security-review.md
→ 攻击面、应用安全、业务安全、事务并发、
  敏感数据、供应链配置、安全指标和安全门禁
```

安全报告必须独立输出，避免严重安全问题被普通代码质量意见掩盖。

------

## 4. 默认只读

`/wewo-review` 默认只进行审查，不直接修改代码。

允许：

- 读取代码和文档；
- 查看 Git Diff；
- 搜索调用关系；
- 运行测试、构建和静态检查；
- 在受控条件下临时安装审查工具；
- 生成审查报告。

默认禁止：

- 修改生产代码；
- 修改测试代码；
- 修改任何工作流文档（包括上游文档）；
- 使用工具自动修复；
- 删除或回滚文件；
- 自动 Commit；
- 自动合并分支；
- 修改需求和测试预期。

发现问题后，应交由 `/wewo-build` 修复，然后重新运行 `/wewo-review` 复审。

------

## 5. 审查依据优先级

### 第一优先级：直接代码证据

必须优先使用：

- 实际 Git Diff；
- 变更相关上下文代码；
- 实际生产代码；
- 实际测试代码；
- 真实测试、构建、Lint、类型检查和扫描结果；
- 仓库已有规范。

### 第二优先级：需求和实施依据

仅当用户明确提供或确认时使用：

- 用户当前需求；
- 原始需求或 `01-prd.md`；
- `02-technical-design.md`；
- `05-implementation-plan.md`；
- `06-implementation-record.md`；
- Issue、验收标准或 Merge Request 描述。

不得自动扫描 `docs/wewo/` 或仓库发现需求文档；发现潜在相关文档时，必须先向用户确认才能纳入审查依据。

其中 `06-implementation-record.md` 只是实现者声明，不能替代实际代码和命令输出。

### 第三优先级：可选辅助材料

`04-test-cases.md` 仅作为可选参考，用于补充：

- 高风险业务场景；
- 关键测试缺口；
- Build 阶段无理由丢弃的 P0/P1 场景。

不能要求实际测试代码与文档中的测试用例一一对应。

### 默认不读取

`03-test-plan.md` 默认不作为代码审查依据。

只有用户明确要求审查“测试策略是否按计划执行”时，才读取它。

------

## 6. 缺少需求材料时的处理

如果存在需求和技术设计，可以检查：

- 是否完整实现需求；
- 是否存在半实现；
- 是否扩大范围；
- 是否偏离设计；
- 是否违反业务、安全和工程约束。

如果不存在需求材料，仍然可以检查：

- 逻辑错误；
- 安全风险；
- 事务、并发和幂等；
- 代码结构；
- 异常处理；
- 测试质量；
- 兼容性；
- 修改范围。

但必须明确说明：

> 缺少原始需求依据，无法确认功能是否完整满足业务目标，本次只能完成代码工程质量与风险审查。

不得根据代码反向编造需求。

------

## 7. 审查范围确定

优先级如下：

```text
用户明确指定范围
→ 使用用户指定范围

存在未提交修改
→ 审查 Staged + Unstaged Diff

没有未提交修改
→ 审查当前分支相对目标分支的 Diff

无法确定目标分支
→ 询问用户，或明确降级为最近一次 Commit
```

开始前必须记录：

- 审查基线；
- 当前分支和 Commit；
- 目标分支或 Commit；
- 实际使用的 Diff 命令；
- Commit 列表；
- 是否包含未提交修改；
- 是否混入与本次任务无关的变更。

不能在没有证据的情况下默认目标分支一定是 `main` 或 `master`。

------

## 8. 以 Diff 为中心

核心审查对象是：

```text
本次实际 Diff
+
Diff 直接依赖或影响的上下文代码
```

需要根据情况读取：

- 被修改函数的调用方；
- 被修改接口的使用方；
- 数据模型和 Repository；
- 权限中间件；
- 事务和缓存边界；
- 消息生产者与消费者；
- 公共工具；
- 相似现有实现；
- 相关测试。

不应一开始扫描整个仓库，并把所有历史问题混入当前报告。

历史问题应单独标记为：

```text
Existing Issue / 非本次变更引入
```

历史问题默认不进入本次问题密度和合并门禁，除非当前变更扩大了其影响或使其变得可触发。

------

## 9. Diff 预分析

启动正式 Reviewer 前，主 Agent 应统计：

- 修改文件数；
- 新增行数；
- 删除行数；
- 生产代码变更行数；
- 测试代码变更行数；
- 配置和迁移代码行数；
- 涉及语言和框架；
- 新增或升级的依赖；
- 接口变化；
- 数据库变化；
- 权限变化；
- 文件操作；
- 外部调用；
- 全局状态变化；
- 高风险业务模块。

应排除或单独统计：

- 自动生成代码；
- Vendor 代码；
- Lock 文件；
- 构建产物；
- Minified 文件；
- 压缩文件；
- 纯格式化变更；
- 无语义的大范围重排。

这一步用于确定审查范围、Reviewer 分配、工具选择和量化指标分母。

------

# 独立审查机制

## 10. 主 Agent 与子 Agent 分工

正式 Review 不应由刚刚实现代码的 Agent 直接完成。

### 主 Agent 负责

- 确定审查范围；
- 获取 Diff；
- 收集需求、设计和仓库规范；
- 分析技术栈、风险和攻击面；
- 运行通用工具；
- 准备独立审查上下文；
- 启动多个 Reviewer；
- 汇总、复核、去重和量化结果；
- 生成最终报告。

### 子 Agent 负责

- 对真实代码做独立判断；
- 返回有文件位置、证据、影响和修复建议的候选问题；
- 不依赖实现者对代码的解释。

Build 阶段的质量检查只能叫：

```text
Implementation Self-check
实现者自检
```

不能替代正式独立 Review。

------

## 11. 干净审查上下文

不能把完整开发对话原样交给 Reviewer。

Reviewer 只接收与职责有关的事实：

- 审查目标；
- 审查范围；
- Git Diff；
- 原始需求；
- 技术设计；
- 实现约束；
- 仓库规则；
- 必要上下文代码；
- 实际测试和工具输出；
- 对应语言、框架和专项审查指南。

不传递：

- 实现者为什么这样设计；
- 实现者对自己代码的评价；
- “这里应该没问题”等主观判断；
- 未被代码证明的解释；
- 与当前审查维度无关的长对话。

原则：

> Reviewer 审查代码和证据，而不是实现者的辩护。

------

## 12. Reviewer 维度

默认按以下维度使用独立子 Agent。

### Reviewer A：需求与设计符合性

检查：

- 是否完整实现需求；
- 是否存在半实现；
- 是否遗漏状态、异常或权限分支；
- 是否增加需求之外的功能；
- 是否改变用户可观察结果；
- 是否违反技术设计；
- 是否违反明确实现约束；
- 关键需求是否有实现和测试证据。

### Reviewer B：仓库规范与代码结构

检查：

- 是否符合仓库明确规范；
- 是否符合项目分层；
- 是否复用现有能力；
- 是否重复实现；
- 是否存在过度抽象；
- 是否职责混乱；
- 是否无理由引入单例或全局状态；
- 是否在共享对象中保存请求或用户状态；
- 是否硬编码配置；
- 是否修改无关代码；
- 是否违反现有异常、依赖和生命周期方式。

仓库规则优先于通用最佳实践。

### Reviewer C：代码正确性与测试质量

检查：

- 逻辑错误；
- 空值和边界；
- 异常路径；
- 状态流转；
- 资源释放；
- 错误恢复；
- 数据转换；
- 测试是否验证公开行为；
- 是否过度 Mock；
- 是否使用弱断言；
- 是否存在假通过；
- 是否遗漏高风险测试。

### Reviewer D：影响与兼容性

检查：

- API 兼容性；
- 数据库兼容性；
- 配置和默认值变化；
- 序列化格式；
- 生命周期；
- 缓存和消息协议；
- 全局状态；
- 历史数据迁移；
- 调用方兼容；
- 回滚能力；
- 回归范围。

### Reviewer E：安全与可靠性

独立检查：

- 认证和授权；
- 资源级权限；
- 输入验证与注入；
- 文件安全；
- 敏感数据；
- 密钥与日志；
- 事务；
- 并发；
- 幂等；
- 重试；
- 数据一致性；
- 外部系统；
- 供应链和配置安全。

不同 Reviewer 不应读取其他 Reviewer 的初步结论。

------

## 13. 子 Agent 不可用时

如果环境不支持子 Agent，不能停止全部审查。

仍然执行：

- Diff 分析；
- 基础语义审查；
- 测试和构建验证；
- 静态工具检查；
- 攻击面分析；
- 有限代码预审。

但结果必须标记为：

```text
非独立预审
```

并明确说明：

- 独立 Reviewer 未执行；
- 当前结果不具备完整上下文隔离；
- 不能将其包装成正式独立 Review。

高风险变更可以因此保持：

```text
无法给出合并结论
```

------

# 安全与可靠性审查

## 14. 安全审查范围

安全审查必须覆盖四个方面。

### 应用安全

- 身份认证；
- 角色和资源级授权；
- IDOR；
- SQL、命令、模板和表达式注入；
- XSS、CSRF、SSRF；
- 文件上传下载；
- 路径穿越；
- 不安全反序列化；
- 敏感信息；
- 密钥和 Token；
- 日志泄露；
- 外部回调；
- API 滥用。

### 业务安全

- 状态机绕过；
- 重复支付、退款和库存回退；
- 参数篡改；
- 价格和数量绕过；
- 审批流程绕过；
- 请求重放；
- 批量接口绕过单条限制；
- 前端隐藏但服务端未校验；
- 跨用户资源操作。

### 可靠性与数据安全

- 并发竞争；
- TOCTOU；
- 重复提交；
- 幂等；
- 事务边界；
- 部分成功；
- 异常回滚；
- 重复消息；
- 重试副作用；
- 缓存一致性；
- 外部系统超时；
- 数据迁移；
- 共享状态污染。

### 供应链与配置安全

- 新增依赖；
- 依赖来源和版本；
- 已知漏洞；
- CORS；
- Debug；
- TLS 校验；
- 默认密码；
- 不安全随机数；
- 加密配置；
- 容器和 CI 配置；
- 密钥泄露。

------

## 15. 安全三级审查

### L1：快速危险模式检查

检查：

- 硬编码密钥；
- 危险执行函数；
- SQL 拼接；
- Shell 拼接；
- TLS 校验关闭；
- 宽泛 CORS；
- 明文密码；
- 用户输入直接进入文件路径。

### L2：Diff 语义审查

分析：

```text
外部输入
→ 校验与转换
→ 身份和权限判断
→ 敏感操作
```

重点审查新增入口、参数、数据写入、文件操作、外部请求、配置和依赖变化。

### L3：跨文件与业务链路审查

追踪：

```text
请求入口
→ Controller
→ Service
→ Repository
→ 数据库
→ 消息队列
→ 外部系统
```

以下变更默认应执行 L3：

- 登录和权限；
- 订单、库存、支付和退款；
- 文件上传下载；
- 外部回调；
- 管理后台；
- 批量操作；
- 数据导入导出；
- 数据库迁移；
- 公网 API；
- 消息队列；
- 密钥和配置。

------

## 16. 攻击面清单

安全 Reviewer 应先识别本次新增或修改的攻击面：

```markdown
| 攻击面 | 本次变化 | 主要风险 | 审查状态 |
|---|---|---|---|
| HTTP 接口 | 新增订单取消接口 | 越权、重放 | 已审查 |
| 数据库写入 | 修改订单和库存 | 事务、并发 | 已审查 |
| 外部回调 | 新增支付通知 | 伪造、重复 | 待验证 |
| 第三方依赖 | 新增解析库 | 供应链 | 已扫描 |
```

只针对实际涉及的攻击面动态加载检查内容，避免机械输出完整安全清单。

------

# 工具策略

## 17. 三层工具能力

### 第一层：基础语义审查

始终执行，不依赖额外工具：

- Git Diff；
- 文件读取；
- 代码搜索；
- 调用链追踪；
- 需求和设计对照；
- 权限、事务和测试语义分析。

没有专业工具也不能停止这一层。

### 第二层：仓库原生工具

优先使用项目已经配置的：

- 单元测试；
- 集成测试；
- 类型检查；
- Lint；
- 格式化检查；
- 编译；
- 构建；
- 覆盖率；
- 数据库迁移检查；
- 项目已有安全规则。

命令必须从项目配置、CI、README、Makefile 或脚本中读取，不能凭经验编造。

### 第三层：可选专项工具

根据技术栈和攻击面动态选择：

- SAST；
- Secret 扫描；
- 依赖漏洞扫描；
- 配置扫描；
- 容器扫描；
- IaC 扫描；
- 复杂度分析；
- API 契约检查；
- License 检查。

专项工具用于增强证据，不是审查开始的前提。

------

## 18. 工具动态安装

缺失工具允许动态安装，但必须分级处理。

### 可自动临时安装

需同时满足：

- 工具在允许清单中；
- 来源可信；
- 使用固定版本；
- 安装在临时隔离环境；
- 不修改项目依赖；
- 不修改 Lock 文件；
- 不需要管理员权限；
- 不启动持久服务；
- 不上传源码；
- 可以完整记录和清理。

### 必须获得用户确认

包括：

- 需要 Docker；
- 下载量较大；
- 系统级安装；
- 管理员权限；
- 启动后台服务；
- 修改项目环境；
- 修改 Lock 文件；
- 上传代码；
- 访问生产环境；
- 工具来源或版本不明确。

### 默认禁止

- `curl | sh`；
- 不明来源二进制；
- 污染全局 Python 或 Node 环境；
- 关闭 TLS 校验；
- 使用生产密钥；
- 自动上传公司代码；
- 修改系统安全策略。

工具安装失败不能终止基础语义审查。

------

## 19. 工具告警处理

工具告警只属于候选证据：

```text
原始告警
→ 定位代码
→ 判断路径是否可达
→ 判断输入是否可控
→ 检查已有防护
→ 确认是否由当前变更引入
→ 根因去重
→ Confirmed / Potential / Rejected
```

不能将工具原始告警数量直接作为正式问题数。

------

# 问题准入与分级

## 20. 问题状态

所有候选问题必须分类为：

```text
Confirmed
已确认问题

Potential
存在合理风险，但证据不足

Unverified
因缺少环境、代码或工具无法确认

Rejected
误报、无关问题或证据不成立
```

只有 `Confirmed` 进入正式问题数量和问题密度。

------

## 21. 正式问题准入条件

正式问题必须同时满足：

1. 问题真实成立；
2. 由本次变更新增、扩大或暴露；
3. 有明确文件、行号或代码范围；
4. 有清晰触发条件；
5. 能说明实际影响；
6. 修复建议可操作；
7. 不与其他问题重复根因。

不能作为正式问题：

- 泛泛最佳实践；
- 没有证据的“可能存在”；
- 个人代码风格偏好；
- 与当前 Diff 无关的历史问题；
- 未复核的工具原始告警；
- 同一根因的重复描述。

## 23. 证据等级

建议使用：

| 等级 | 证据                               |
| ---- | ---------------------------------- |
| E1   | 静态代码和明确调用路径             |
| E2   | 代码证据加仓库原生静态工具         |
| E3   | 代码证据加真实测试、构建或运行结果 |
| E4   | 代码证据加专项工具和独立复核       |

证据等级表示结论可靠程度，不代表问题严重程度。

------

## 24. 严重程度

### Critical

例如：

- 远程代码执行；
- 核心权限体系完全绕过；
- 大规模敏感数据泄露；
- 重大资金或数据损失；
- 有效生产密钥泄露。

必须阻止合并和发布。

### High

例如：

- 资源级越权；
- 管理权限绕过；
- SQL 或命令注入；
- 核心业务逻辑错误；
- 事务和数据一致性破坏；
- 任意文件读写；
- 严重兼容性破坏。

必须阻止合并。

### Medium

例如：

- 重要边界遗漏；
- 异常处理不足；
- 敏感日志；
- 重要测试缺口；
- 局部数据风险；
- 明显维护性问题。

一般应修复，或由负责人明确接受风险。

### Low

例如：

- 局部可读性；
- 轻微重复；
- 非阻塞规范问题；
- 低影响安全加固建议。

可以后续处理，但需要记录。

------

# 量化指标

## 25. 代码行数统计

分别统计：

- 生产代码变更行数；
- 测试代码变更行数；
- 配置和迁移代码行数；
- 有效可审查代码行数；
- 实际完成审查代码行数。

变更代码行数可以采用：

```text
新增行数 + 删除行数
```

排除自动生成代码、Vendor、Lock、构建产物和纯格式化变更。

------

## 26. 问题密度

```text
确认问题密度
=
Confirmed 问题数
÷
实际审查生产代码 KLOC
严重问题密度
=
Critical + High 问题数
÷
实际审查生产代码 KLOC
安全问题密度
=
Confirmed 安全问题数
÷
实际审查生产代码 KLOC
```

测试质量问题应使用测试代码 KLOC 作为分母。

------

## 27. 加权问题密度

建议权重：

| 严重程度 | 权重 |
| -------- | ---- |
| Critical | 8    |
| High     | 5    |
| Medium   | 2    |
| Low      | 1    |

计算：

```text
加权问题密度
=
Σ（问题数 × 严重程度权重）
÷
实际审查生产代码 KLOC
```

问题密度主要用于同一项目的长期趋势分析，不能单独作为合并门禁。

------

## 28. Review 有效性指标

至少统计：

- 原始候选问题数；
- Confirmed 数；
- Potential 数；
- Unverified 数；
- Rejected 数；
- 候选确认率；
- 根因去重后问题数；
- 审查代码覆盖率；
- 需求实现映射率；
- 需求测试映射率；
- 高风险场景测试覆盖率；
- 工具验证覆盖率；
- 未解决阻塞项数量。

其中：

```text
候选确认率
=
Confirmed
÷
所有候选问题
审查代码覆盖率
=
实际审查 LOC
÷
有效可审查 LOC
```

------

## 29. 安全指标

安全报告至少统计：

- 新增或修改攻击面数量；
- 已审查攻击面数量；
- 攻击面审查覆盖率；
- Confirmed 安全问题数；
- Critical、High、Medium、Low 分布；
- 严重安全问题数；
- 安全问题密度；
- 安全候选确认率；
- 高风险链路测试覆盖率；
- 工具告警人工复核率；
- 未解决安全阻塞项数量。

关键安全目标：

```text
未解决 Critical = 0
未解决 High = 0
高风险攻击面审查覆盖率 = 100%
```

------

## 30. 小型 Diff

当有效变更少于约 200 行时，每千行问题数容易被放大。

因此：

```text
小型 Diff
→ 重点展示实际问题数量、严重程度和阻塞项

中大型 Diff
→ 同时展示问题数量和问题密度

长期 KPI
→ 使用月度、季度或累计至少 1000 行的数据
```

不能根据一次几十行的修改评价整个团队或项目质量。

# 审查结论

## 31. 代码审查结论

分为：

```text
通过
条件通过
不通过
无法给出合并结论
```

### 通过

要求：

- Critical 为 0；
- High 为 0；
- 核心需求遗漏为 0；
- 相关测试通过；
- 构建和必要质量检查通过；
- 没有未解决阻塞项。

### 条件通过

没有 Critical 和 High，但存在可以接受的 Medium 或 Low。

必须记录：

- 接受条件；
- 剩余风险；
- 后续处理方式；
- 风险接受人。

### 不通过

存在以下任一情况：

- 未解决 Critical；
- 未解决 High；
- 核心需求遗漏；
- 明显业务错误；
- 权限或数据一致性风险；
- 相关测试失败；
- 构建失败；
- 严重兼容性破坏。

### 无法给出合并结论

例如：

- Diff 不完整；
- 关键代码缺失；
- 关键环境不可用；
- 权限、事务或外部行为无法验证；
- 独立 Reviewer 未完成；
- 高风险安全链路无法确认。

即使无法给出结论，也应输出已经完成的审查和发现的问题。

------

## 32. 安全门禁结论

安全报告单独给出：

```text
通过
不通过
未完成 / 无法确认
```

以下情况安全门禁必须不通过：

- 未解决 Critical；
- 未解决 High；
- 有效密钥泄露；
- 资源级权限无法保证；
- 核心交易缺少事务或幂等；
- 高风险入口未完成安全审查；
- 关键安全测试失败。

即使普通代码审查通过，只要安全门禁不通过，就不能给出可合并结论。

## 35. 最终输出说明

执行完成后，应向用户说明：

- 实际审查范围；
- 审查基线；
- 使用了哪些需求和设计材料；
- 启动了哪些独立 Reviewer；
- 使用了哪些工具；
- 哪些工具进行了动态安装；
- 哪些验证未完成；
- Confirmed 问题总数；
- Critical、High、Medium、Low 分布；
- 每千行确认问题数；
- 安全问题和阻塞项；
- 代码审查结论；
- 安全门禁结论；
- 两个报告文件的位置。

不能只输出：

```text
审查完成，代码质量良好。
```

## 36. 核心硬规则

生成的 Skill 应明确遵守：

```text
1. 以实际 Git Diff 为主要审查对象。

2. 正式 Review 应优先由新的独立子 Agent 执行。

3. 实现者自检不能替代独立 Review。

4. 需求、规范、正确性、影响和安全必须分维度审查。

5. 仓库明确规则优先于通用最佳实践。

6. 每个正式问题必须有代码位置、证据、触发条件、影响和修复建议。

7. 只有 Confirmed 问题进入正式问题密度。

8. 当前变更问题和历史问题必须分开。

9. 同一根因只能统计一次。

10. 工具输出只是候选证据，必须经过语义复核。

11. 没有额外工具也必须继续基础语义审查。

12. 缺失工具可以在固定版本、可信来源和隔离环境中动态安装。

13. 高影响安装、系统修改、源码上传和持久服务必须先获得用户确认。

14. 工具安装失败后继续审查，并记录未验证范围。

15. 不得将未执行的测试或扫描写成“通过”。

16. 默认只审查，不自动修改代码。

17. Critical 和 High 问题必须阻止合并。

18. 安全门禁独立于普通代码质量结论。

19. 不能用问题密度单独决定是否允许合并。

20. 最终结论必须基于最新代码、测试和工具证据。
```

------

## 37. Skill 最终职责

`/wewo-review` 的最终职责可以概括为：

> 基于实际代码 Diff，收集当前可用的需求、技术设计、实施记录和仓库规范，由多个干净上下文的独立子 Agent 分别审查需求与设计符合性、仓库规范与代码结构、代码正确性与测试质量、影响兼容性以及安全可靠性；结合仓库原生工具和可选专项工具，对所有候选问题进行证据复核、当前变更归因、严重程度校准和根因去重，最终生成可量化、可追踪并具有明确合并门禁的代码审查报告与安全审查报告。
