# `wewo-build` Skill 需求说明

## 1. Skill 定位

`/wewo-build` 是 `wewo-skills` 中负责代码实现的 Skill。

它综合当前可用的需求材料、技术设计、测试用例和现有项目代码，先制定实施计划，再将适合开发阶段验证的业务行为转换为真实的单元测试、应用服务测试或集成测试，通过 TDD 逐步完成代码实现。

本 Skill 不只是“根据文档生成代码”，而是负责完成以下闭环：

```text
理解开发目标
    ↓
分析现有项目
    ↓
确定实现约束
    ↓
评估 TDD 候选
    ↓
确定测试接缝
    ↓
拆分纵向实现切片
    ↓
逐个执行 TDD
    ↓
进行切片级质量检查
    ↓
执行整体回归与质量验证
    ↓
记录实际实现结果
```

最终新增两个文档：

```text
05-implementation-plan.md
06-implementation-record.md
```

同时可能新增或修改：

- 业务实现代码；
- 单元测试代码；
- 集成测试代码；
- 接口测试代码；
- 数据库迁移文件；
- 配置文件；
- 必要时补充更新 `04-test-cases.md`。

------

## 2. Skill 独立性

`/wewo-build` 可以独立运行，不强制要求用户先运行：

```text
/wewo-prd
/wewo-erd
/wewo-testplan
```

用户可以直接提供：

- 一句话或一段明确的开发任务；
- Issue、Bug 描述或变更说明；
- PRD 或其他需求文档；
- `01-prd.md`；
- 技术设计文档；
- `02-technical-design.md`；
- 测试计划；
- `03-test-plan.md`；
- 测试用例；
- `04-test-cases.md`；
- 当前项目代码；
- 多种材料的组合。

仅当用户明确选择或确认上游文档时（显式提供工作区、显式引用文档、或要求继续某个已有需求），才应读取和复用。不得自动扫描 `docs/wewo/` 或仓库寻找历史工作流文档；文档存在于工作区本身不构成读取授权；发现潜在相关文档时，必须先向用户确认才能使用。

如果不存在被授权的上游文档，也不能拒绝执行，而应根据用户描述、现有项目和必要的多轮对话，补齐本次实现所需的最小信息。

不同 Skill 之间保持松耦合：

```text
可以独立使用；
也可以连续使用；
存在且被用户明确选用的上游产物时复用；
不存在被授权的上游产物时仍能正常运行。
```

------

## 3. 可接受的输入

`/wewo-build` 可以综合分析：

- 当前用户指令；
- 当前对话中的需求信息；
- PRD、技术设计、测试计划和测试用例；
- Markdown、TXT、Word、Excel、PPT、PDF 等文档；
- 页面截图、原型或接口说明；
- Issue、任务单、缺陷描述；
- 当前项目代码；
- 项目已有测试；
- Git Diff；
- 项目已有编码规范；
- 多份相关材料。

不得默认某一个文件是唯一事实来源。

上述输入仅在用户当前交互中提供、显式引用、或经用户明确确认后才可使用；不得自动扫描工作区或仓库发现历史文档。

如果材料之间存在冲突，应先指出冲突，并确认最终实现依据。

------

## 4. 核心目标

`/wewo-build` 需要完成：

1. 收集并理解当前开发任务；
2. 分析现有项目、架构和测试基础；
3. 确认本次实现范围和非实现范围；
4. 提取安全、可靠性和代码结构约束；
5. 评估测试计划中的 TDD 候选；
6. 为实际采用的业务行为确定真实测试接缝；
7. 将工作拆分为独立可验证的纵向切片；
8. 生成并确认 `05-implementation-plan.md`；
9. 对每个切片执行真实 TDD；
10. 每个切片完成后进行需求符合性和代码质量检查；
11. 运行局部测试、类型检查、Lint 和构建检查；
12. 所有切片完成后执行整体回归和最终验证；
13. 在 `06-implementation-record.md` 中记录测试用例调整和与测试计划的差异，不修改上游测试文档；
14. 持续记录并最终生成 `06-implementation-record.md`。

------

## 5. 开发目标充分性判断

修改代码前，至少需要明确：

- 本次要实现、修改或修复什么；
- 用户或调用方可观察到什么结果；
- 哪些业务规则必须满足；
- 哪些内容明确不属于本次范围；
- 是否存在关键权限或安全要求；
- 是否涉及数据一致性；
- 是否允许修改接口、数据库或依赖；
- 如何判断本次实现完成。

如果信息已经足够，应直接进入项目分析。

如果只缺少少量会影响实现的问题，应在当前阶段询问，例如：

- 是否允许修改现有接口；
- 是否允许新增数据库字段；
- 是否允许引入新依赖；
- 失败时应该回滚还是允许部分成功；
- 是否需要兼容历史数据；
- 是否需要审计日志。

如果需求仍然模糊到无法判断用户可观察结果，不得直接编写代码。

只有当用户希望完整重新梳理需求时，才建议使用 `/wewo-prd`，但不能将其作为强制前置条件。

------

## 6. 先分析项目，再制定实现方案

开始实现前，应主动读取当前项目中与需求相关的内容，包括：

- 项目语言和框架；
- 包管理工具；
- 目录结构；
- 系统分层；
- 相关页面、组件、模块和服务；
- 已有接口；
- 已有数据模型；
- 身份认证和权限方式；
- 依赖注入方式；
- 对象生命周期；
- 数据库和事务方式；
- 日志和异常处理；
- 缓存、消息队列和定时任务；
- 测试框架；
- 测试目录；
- Fixture 和测试数据准备方式；
- Mock 和 Fake 的使用方式；
- Lint；
- 格式化工具；
- 类型检查；
- 构建命令；
- 项目已有的相似实现；
- 当前 Git 分支和工作区状态。

不得编造项目中不存在的：

- 文件；
- 类；
- 函数；
- 接口；
- 数据表；
- 测试框架；
- 构建命令。

应优先复用项目已有架构、测试接缝和公共能力。

------

## 7. Git 与工作区检查

修改代码前，应检查：

- 当前是否位于 Git 仓库；
- 当前分支；
- 工作区是否存在未提交修改；
- 当前修改是否属于用户正在进行的其他工作；
- 是否需要创建新分支或 Git Worktree。

不得覆盖、删除或回滚用户已有的未提交修改。

对于风险较高、修改范围较大或工作区不干净的任务，可以建议创建独立分支或 Worktree。

如果当前环境不适合自动创建，不应强制执行，但必须说明工作区风险。

默认不自动提交或合并代码，除非用户明确要求。

------

## 8. 实现基线

正式制定计划前，应总结本次实现基线：

```text
要实现什么；
不实现什么；
必须满足哪些业务行为；
必须遵守哪些技术约束；
哪些材料是本次实现依据；
哪些问题仍未解决。
```

如果存在 `02-technical-design.md`，其中的“实现约束”应被视为编码阶段的重要约束。

例如：

- 必须复用现有模块；
- 权限校验必须在服务端完成；
- 不得使用手写可变单例；
- 不得在共享对象中保存用户或请求状态；
- 数据更新必须保持事务一致性；
- 不得修改非本次范围模块；
- 不得引入未经确认的新依赖；
- 必须沿用现有异常和响应格式。

如果没有技术设计文档，应根据现有项目提取最小必要约束。

------

## 9. 全局实现约束

`05-implementation-plan.md` 中必须包含“全局实现约束”。

约束根据当前项目和需求动态生成，通常包括：

- 遵循项目现有架构和分层；
- 优先复用现有模块与公共能力；
- 不无理由引入新的设计模式；
- 不无理由创建单例或全局可变状态；
- 不在共享对象中存储用户级或请求级数据；
- 不硬编码密码、Token、密钥和环境配置；
- 不依赖前端完成服务端权限控制；
- 不吞掉异常；
- 不修改需求范围外的代码；
- 不为了测试通过修改业务预期；
- 不引入未经确认的新依赖；
- 不通过放宽断言让测试通过；
- 不在生产代码中添加仅用于测试的特殊逻辑；
- 不针对测试输入写死返回值；
- 保持代码具有清晰的测试边界；
- 保持与已有项目风格一致。

------

## 10. TDD 候选评估

如果存在 `04-test-cases.md`，应优先筛选：

```text
TDD 候选：是
```

但不能将所有候选直接转换为测试代码。

每条候选应被评估为：

- 直接采用；
- 调整测试层级；
- 拆分；
- 合并；
- 延后到 `/wewo-test`；
- 不采用；
- 被环境阻塞；
- 待确认。

建议形成评估表：

```markdown
| 用例 | 评估结果 | 最终测试层级 | 处理说明 |
|---|---|---|---|
| TC-001 | 直接采用 | 应用服务测试 | 公开行为明确 |
| TC-002 | 调整层级 | 接口集成测试 | 权限逻辑位于 API 层 |
| TC-003 | 拆分 | 单元 + 集成 | 同时包含业务规则和事务 |
| TC-004 | 延后 | E2E | 需要完整页面环境 |
| TC-005 | 不采用 | — | 验证内部方法调用次数 |
```

评估重点是：

- 输入条件；
- 用户或调用方行为；
- 可观察的业务结果。

不能被测试用例中预设的类名、方法名、Mock 方式或内部结构绑定。

------

## 11. 没有测试用例文档时的处理

如果不存在 `04-test-cases.md`，`/wewo-build` 应根据：

- 当前需求；
- 技术设计；
- 现有代码；
- 项目已有测试；

提取最小必要的开发行为。

例如：

```text
1. 待发货订单允许取消；
2. 已发货订单禁止取消；
3. 非订单所属用户禁止取消；
4. 重复取消不得重复修改库存；
5. 库存回退失败时订单状态不得提交。
```

这些行为应先向用户进行简洁总结。

确认后，再进入测试接缝选择和纵向切片。

不需要因此重新生成完整的测试计划和测试用例文档。

------

## 12. 测试接缝

在编写测试前，应确定每个业务行为通过哪个公开边界进行验证。

测试接缝可以包括：

- 领域对象的公开行为；
- 应用服务；
- HTTP API；
- Repository 与测试数据库；
- 消息消费者；
- 命令行入口；
- 前端组件公开行为。

选择原则：

1. 优先复用项目已有测试接缝；
2. 优先通过稳定公开接口验证行为；
3. 尽量验证用户或调用方可观察结果；
4. 避免测试私有方法；
5. 避免断言内部模块的调用次数；
6. 避免用大量 Mock 锁死实现结构；
7. 一个业务能力尽量使用较少且稳定的主要测试接缝。

例如：

```markdown
| 业务行为 | 测试接缝 | 原因 |
|---|---|---|
| 非法订单状态禁止取消 | 订单取消应用服务 | 可以完整观察业务结果 |
| 用户不能取消他人订单 | HTTP API | 权限由 API 层处理 |
| 状态和库存共同回滚 | 服务 + 测试数据库 | 需要验证真实事务 |
| 页面取消流程 | 浏览器页面 | 留给后续 E2E |
```

如果项目中已经存在明确测试方式，应直接沿用。

只有存在多个合理方案且会明显影响实现时，才需要用户确认。

------

## 13. 纵向实现切片

实施任务必须按照可独立验证的业务行为进行拆分。

避免按照技术层拆分：

```text
修改 Model；
修改 Service；
修改 Controller；
最后补测试。
```

应优先拆成：

```text
切片 1：支持待发货订单正常取消；
切片 2：禁止非法状态取消；
切片 3：保证订单和库存事务一致；
切片 4：保证重复取消幂等；
切片 5：接入前端取消流程。
```

每个切片应包含：

- 业务目标；
- 用户或调用方可观察结果；
- 对应测试用例或需求；
- 测试接缝；
- 建议测试层级；
- 预计修改范围；
- 验证命令；
- 完成条件；
- 相关实现约束；
- 与其他切片的依赖关系。

每个切片都应足够小，能够独立测试和审查。

------

## 14. 实施计划确认

修改代码前，先生成 `05-implementation-plan.md`。

计划应向用户总结：

- 实现目标；
- 实现依据；
- 当前项目分析；
- 修改范围和非修改范围；
- 全局实现约束；
- TDD 候选评估；
- 测试接缝；
- 纵向实现切片；
- 接口、数据库和依赖变化；
- 验证方式；
- 风险和未决问题。

然后询问：

```text
以上实施计划是否符合本次开发目标？

确认后我将按照纵向切片和 TDD 方式开始修改代码。
```

只有用户确认后，才开始实际修改代码。

如果用户明确要求直接执行，且开发目标已经足够清晰，可以不进行冗长确认，但仍应生成实施计划作为执行依据。

------

## 15. TDD 执行原则

TDD 是 `/wewo-build` 的主要实现方法。

基本循环：

```text
选择一个最小业务行为
    ↓
编写一个失败测试
    ↓
运行并确认有效失败
    ↓
编写最小生产实现
    ↓
运行并确认通过
    ↓
进行必要的小范围整理
    ↓
再次运行相关测试
```

不能一次性编写全部测试，再一次性编写全部实现。

应遵循：

```text
一个测试接缝；
一个业务行为；
一个失败测试；
一个最小实现。
```

------

## 16. Red 阶段

Red 阶段必须：

1. 针对一个明确业务行为编写测试；
2. 使用项目已有测试框架；
3. 真实运行测试；
4. 确认测试确实失败；
5. 确认失败原因是目标行为尚未实现或行为不符合预期。

以下情况不属于有效 Red：

- 测试语法错误；
- 导入失败；
- Fixture 缺失；
- 依赖未安装；
- 数据库无法连接；
- 环境无法启动；
- 测试框架配置错误；
- 当前项目已有基础错误。

这些问题应先修复，再重新确认 Red。

不得在没有有效失败证据的情况下直接编写生产代码。

------

## 17. Green 阶段

Green 阶段只编写使当前行为通过所需的最小生产实现。

“最小实现”必须同时满足：

- 满足当前业务行为；
- 符合现有项目架构；
- 遵守全局实现约束；
- 能够继续演进；
- 不破坏已有行为。

禁止：

- 根据测试输入写死返回结果；
- 为单个测试添加特殊生产分支；
- 在生产代码中判断是否处于测试环境；
- 通过删除或弱化断言让测试通过；
- 通过修改业务预期迁就实现；
- 顺便实现后续全部功能；
- 修改大量无关代码；
- 提前引入复杂抽象；
- 复制已有逻辑而不复用；
- 吞掉异常；
- 未经确认引入新依赖。

实现后必须真实运行当前测试并确认通过。

------

## 18. 小范围重构

测试通过后，可以进行必要的小范围整理：

- 改善命名；
- 删除明显重复；
- 拆分刚产生的过长函数；
- 提取小型辅助逻辑；
- 简化条件分支；
- 改善与周围代码的一致性。

不应在每次 Green 后进行：

- 大规模模块重构；
- 全局架构调整；
- 无关代码清理；
- 大量文件重命名；
- 新增复杂抽象层；
- 修改当前切片之外的业务行为。

整理后必须重新运行相关测试。

大范围重构问题可以记录并交由后续 `/wewo-review` 评估。

------

## 19. 单元测试与集成测试

### 19.1 单元或应用服务测试

主要驱动：

- 业务规则；
- 输入校验；
- 状态判断；
- 权限判断；
- 数据转换；
- 边界条件；
- 异常行为；
- 幂等规则；
- 独立模块行为。

这些测试应：

- 执行快速；
- 结果稳定；
- 不依赖生产环境；
- 不依赖真实外部网络；
- 尽量通过公开行为验证结果。

### 19.2 集成测试

用于验证：

- 业务服务与数据库；
- Repository 持久化；
- API 与服务层；
- 事务；
- 缓存；
- 消息队列；
- 文件系统；
- 外部服务适配器；
- 多模块协作。

推荐节奏：

```text
完成若干相关单元 TDD
    ↓
补充或执行对应集成测试
    ↓
确认纵向切片整体可用
```

集成测试也可以提前编写，但不应完全替代快速单元测试内循环。

------

## 20. Mock 使用原则

尽量只 Mock 系统外部边界，例如：

- 第三方支付；
- 邮件或短信服务；
- 时间；
- 随机数；
- 外部 HTTP 服务；
- 不可控文件系统；
- 外部消息平台。

尽量不要 Mock：

- 自己编写的内部类；
- 内部业务模块；
- 当前项目可直接运行的协作者；
- 为了断言调用次数而创建的内部 Mock。

优先验证：

```text
输入
→ 公开行为
→ 可观察结果
```

避免验证：

```text
私有方法；
内部调用顺序；
内部对象调用次数；
具体类拆分方式。
```

------

## 21. 浏览器 E2E 的职责边界

浏览器 E2E 不属于 `/wewo-build` 的执行职责。

`/wewo-build` 主要负责：

- 单元测试；
- 应用服务测试；
- 集成测试；
- 必要的接口测试；
- 现有的快速回归测试。

`/wewo-build` 不得：

- 检查 Playwright 或 Cypress 是否安装；
- 检查浏览器可用性；
- 安装 Playwright、Cypress 或浏览器；
- 创建浏览器 E2E 基础设施或新的浏览器 E2E 测试；
- 执行浏览器 E2E；
- 询问用户是否应安装或启用浏览器 E2E；
- 将浏览器 E2E 作为 Build 完成条件。

当 Build 遇到被分类为 E2E 的测试用例时：

- 保留其预期业务行为；
- 识别为超出 Build 执行职责；
- 留给独立的测试执行阶段；
- 不检查 E2E 工具；
- 不将其标记为 Passed；
- 不修改上游测试用例文档来记录 Build 执行状态；
- 将相关交接说明记录在 `06-implementation-record.md` 中。

所有具体的浏览器 E2E 行为（工具选择、安装、脚本生成和执行）属于 `/wewo-test`。

------

## 22. 每个切片的完成条件

每个纵向切片不能只以“新测试通过”为完成标准。

至少需要满足：

1. 新测试真实运行并按预期失败过；
2. 实现后新测试通过；
3. 当前相关旧测试通过；
4. 必要集成测试通过；
5. 类型检查或编译通过；
6. 没有新增明显 Lint 错误；
7. 没有超出计划修改范围；
8. 没有违反全局实现约束；
9. 没有为了通过测试改变业务预期；
10. 已完成切片级需求符合性检查；
11. 已完成切片级代码质量检查；
12. 已更新实施记录。

------

## 23. 切片级需求符合性检查

每个切片完成后，先检查：

- 是否实现了切片要求的业务行为；
- 是否遗漏了要求；
- 是否增加了没有要求的功能；
- 是否改变了用户可观察结果；
- 是否违反需求范围；
- 是否违反技术设计；
- 是否违反安全和一致性要求；
- 测试是否覆盖了目标行为。

需求符合性未通过时，不得进入下一个切片。

------

## 24. 切片级代码质量检查

需求符合性通过后，再检查：

- 是否存在针对测试的硬编码；
- 是否存在重复逻辑；
- 是否无必要地引入单例或全局状态；
- 是否在共享对象中保存请求或用户数据；
- 是否无理由引入新依赖；
- 是否破坏项目分层；
- 是否把多个无关职责放入同一个类；
- 是否存在过度抽象；
- 是否存在明显过长函数或复杂条件；
- 异常处理是否合理；
- 权限校验位置是否正确；
- 测试是否过度 Mock；
- 测试是否锁死内部实现；
- 是否修改了无关代码；
- 是否残留调试代码和临时日志。

发现问题后，应修复并重新运行相关测试。

------

## 25. 子 Agent 与独立审查

如果运行环境支持子 Agent，可以考虑：

- 每个边界清晰的纵向切片交给新的实现 Agent；
- 实现 Agent只接收当前任务、必要项目背景和全局约束；
- 实现完成后由独立 Reviewer 检查实际 Diff；
- Reviewer 不依赖实现者的主观解释；
- 审查问题修复后再次复查。

如果环境不支持子 Agent，则由当前 Agent执行，但在审查阶段应切换为只读审查视角，重新读取：

- 实施计划；
- 当前 Git Diff；
- 测试代码；
- 最新测试结果。

子 Agent不是强制要求，不能因为环境不支持而阻塞开发。

------

## 26. 质量检查与验证频率

开发过程中应频繁执行局部验证，包括：

- 当前新增测试；
- 当前测试文件；
- 受影响模块测试；
- 类型检查；
- 编译；
- 必要的 Lint。

不要每写一行代码就运行完整测试套件，也不能等全部代码完成后才第一次运行测试。

全部切片完成后，应重新执行：

- 所有新增测试；
- 受影响模块测试；
- 必要集成测试；
- 回归测试；
- 类型检查；
- Lint；
- 构建命令；
- 当前可执行的完整测试套件。

------

## 27. 完成声明必须基于最新证据

不能因为之前某次测试通过，就直接声称最终实现完成。

完成前必须：

1. 明确哪些命令能够证明实现正确；
2. 重新执行这些命令；
3. 阅读完整输出；
4. 检查退出码和失败数量；
5. 根据最新结果记录结论。

必须区分：

```text
已实际执行并通过；
已实际执行但失败；
未执行；
无法执行；
环境阻塞；
仅执行了局部测试；
完整测试套件未执行。
```

不能把“代码看起来正确”写成“测试通过”。

不能完全相信子 Agent 或之前记录的“测试通过”，主流程需要基于最新证据重新验证。

------

## 28. 测试用例文档的更新边界

`/wewo-build` 不得修改 `03-test-plan.md` 或 `04-test-cases.md`，也不得在它们不存在时创建空文件。

实现阶段产生的调整（评估结果、最终测试层级、实际测试接缝、实际测试文件、TDD 采用状态、用例拆分或合并、自动化方式、延后或不采用的原因）应记录在 `06-implementation-record.md` 中，并向用户说明。

### 不得修改的内容

- 业务规则；
- 用户可观察结果；
- 权限要求；
- 数据一致性要求；
- 安全要求；
- 验收结果；
- 需求范围。

如果实现发现业务预期无法满足，应暂停并说明冲突，不能修改测试预期迁就代码。

如果上游测试文档确实需要修正（例如整体测试策略被证明无法执行），应通过显式用户确认后，由该文档的所属阶段（`/wewo-testplan`）或有明确授权的修订来完成。

------

## 29. 实现偏差处理

允许根据真实项目调整：

- 测试层级；
- 测试接缝；
- 文件拆分；
- 内部类和函数结构；
- 用例拆分与合并；
- 具体实现细节。

不得未经确认调整：

- 业务规则；
- 权限规则；
- 用户可观察结果；
- 数据一致性要求；
- 安全要求；
- 明确需求范围。

如果实际实现与计划不同，应记录：

- 原计划；
- 实际方案；
- 调整原因；
- 是否影响业务预期；
- 是否获得用户确认；
- 影响的文件和测试。

不能静默偏离技术设计和测试预期。

------

# `05-implementation-plan.md`

## 30. 文档定位

`05-implementation-plan.md` 是修改代码前的实施计划。

它回答：

> 本次准备如何实现、如何测试、如何控制修改范围和代码质量？

------

## 31. 固定核心结构

```markdown
# 实施计划

## 1. 实现目标

## 2. 实现依据

## 3. 当前项目分析

## 4. 实现范围

### 4.1 本次修改范围

### 4.2 非本次修改范围

## 5. 全局实现约束

## 6. TDD 候选评估

## 7. 测试接缝

## 8. 纵向实现切片

## 9. 接口、数据库与依赖变更

## 10. 验证计划

## 11. Git 与工作区策略

## 12. 风险与未决问题
```

没有涉及的动态内容可以省略或简写。

------

## 32. 实现目标

说明：

- 本次要实现什么；
- 用户或调用方最终获得什么能力；
- 什么结果表示开发完成。

------

## 33. 实现依据

列出实际使用的材料，例如：

- 用户需求描述；
- `01-prd.md`；
- `02-technical-design.md`；
- `03-test-plan.md`；
- `04-test-cases.md`；
- 当前项目代码；
- 本阶段多轮对话确认结果。

不能为了格式完整而列出不存在的文件。

------

## 34. 当前项目分析

记录实际读取到的相关项目事实：

- 技术栈；
- 相关模块；
- 可复用能力；
- 测试框架；
- 测试接缝；
- 质量检查命令；
- 当前 Git 状态。

不能编造项目内容。

------

## 35. TDD 候选评估

使用表格记录：

```markdown
| 用例或行为 | 评估结果 | 最终测试层级 | 测试接缝 | 说明 |
|---|---|---|---|---|
```

没有 `04-test-cases.md` 时，可直接列出从需求中提取的 TDD 行为。

------

## 36. 纵向实现切片

```markdown
### Slice-001 切片名称

- **业务目标**：

- **用户可观察结果**：
- **测试接缝**：
- **测试层级**：

- **实现约束**：
- **验证命令**：
- **完成条件**：
- **依赖切片**：
```

------

## 37. 验证计划

说明：

- 每个切片运行什么测试；
- 什么时候运行集成测试；
- 什么时候运行类型检查；
- 什么时候运行完整测试套件；
- 最终构建和回归方式。

不得编造不存在的命令。

# `06-implementation-record.md`

## 38. 文档定位

`06-implementation-record.md` 是编码过程中持续更新，并在实现完成后整理的实施记录。

它回答：

> 实际修改了什么、测试了什么、验证结果是什么、与原计划有什么差异？

------

## 39. 固定核心结构

```markdown
# 实施记录

## 1. 实现结果概述

## 2. 实际修改文件

## 3. 纵向切片完成情况

## 4. TDD 执行记录

## 5. 单元测试与集成测试结果

## 6. 质量检查结果

## 7. 测试用例调整情况

## 8. 与实施计划的差异

## 9. 未完成事项与已知限制

## 10. 最终验证证据

## 11. 最终结论
```

------

## 40. 实际修改文件

建议记录：

```markdown
| 文件 | 变更类型 | 变更内容 |
|---|---|---|
| `path/to/file` | 新增 / 修改 / 删除 | 简要说明 |
```

------

## 41. 纵向切片完成情况

建议记录：

```markdown
| 切片 | 状态 | 测试状态 | 审查状态 | 说明 |
|---|---|---|---|---|
```

状态可以使用：

- 未开始；
- 进行中；
- 已完成；
- 被阻塞；
- 已取消。

------

## 42. TDD 执行记录

不要求记录每一行终端输出，但应保留关键证据：

```markdown
### Slice-001 / Behavior-001

- **测试文件**：
- **Red 命令**：
- **Red 结果**：
- **失败原因**：
- **实现内容**：
- **Green 命令**：
- **Green 结果**：
- **重构内容**：
- **重构后验证**：
```

不得伪造未实际运行的结果。

------

## 43. 测试与质量检查结果

建议使用：

```markdown
| 检查项 | 执行命令 | 结果 | 说明 |
|---|---|---|---|
| 新增单元测试 | `...` | 通过 / 失败 / 未执行 | |
| 集成测试 | `...` | 通过 / 失败 / 阻塞 | |
| 类型检查 | `...` | 通过 / 失败 | |
| Lint | `...` | 通过 / 失败 | |
| 构建 | `...` | 通过 / 失败 | |
| 完整测试套件 | `...` | 通过 / 失败 / 未执行 | |
```

------

## 44. 测试用例调整情况

记录：

- 哪些 TDD 候选被直接采用；
- 哪些调整了层级；
- 哪些被拆分或合并；
- 哪些延后到 `/wewo-test`；
- 哪些无法采用；
- 是否更新了 `04-test-cases.md`。

------

## 45. 最终验证证据

必须记录完成前最新执行的验证结果：

- 执行时间；
- 执行命令；
- 退出状态；
- 通过和失败数量；
- 未执行项目；
- 环境阻塞；
- 剩余风险。

只有最新证据支持结论时，才能写“实现完成”。

------

## 46. 输出要求

`/wewo-build` 最终新增：

```text
05-implementation-plan.md
06-implementation-record.md
```

同时直接新增或修改：

- 业务代码；
- 单元测试代码；
- 集成测试代码；
- 必要接口测试；
- 数据库迁移；
- 必要配置。

根据实际情况，在 `06-implementation-record.md` 中记录测试用例调整与测试计划差异；不修改上游测试文档。

生成完成后，应向用户说明：

- 实现计划和实施记录的位置；
- 实际完成的功能；
- 新增或修改的主要文件；
- 测试和质量检查结果；
- 是否更新了测试用例；
- 是否存在未完成事项或剩余风险。

不要因为 Build 已完成而自动声称代码已经通过最终独立审查。

完整代码审查由后续 `/wewo-review` 负责。

------

## 47. 代码质量要求

最终实现应满足：

- 与当前需求一致；
- 遵守技术设计和实现约束；
- 优先复用现有项目能力；
- 采用独立可验证的纵向切片；
- TDD 测试真实经历有效 Red 和 Green；
- 测试验证公开行为；
- 不过度 Mock；
- 不为测试写死生产代码；
- 不通过弱化测试迁就实现；
- 不无理由创建单例和全局状态；
- 不在共享对象中保存用户或请求数据；
- 不硬编码敏感配置；
- 不修改无关代码；
- 不引入未经确认的依赖；
- 每个切片通过需求符合性与代码质量检查；
- 完成声明基于最新验证证据；
- 对无法执行的测试和剩余风险保持透明。

------

## 48. `/wewo-build` 不负责的内容

本 Skill 不负责：

- 完整重新生成 PRD；
- 完整重新设计测试计划；
- 检查或安装 Playwright、Cypress 等浏览器 E2E 工具与浏览器；
- 浏览器 E2E 的生成和执行；
- 浏览器兼容性验收；
- 人工探索测试；
- 大规模性能测试；
- 最终独立安全审查；
- 最终独立代码审查；
- 自动合并代码；
- 未经用户要求自动提交代码；
- 自动进入后续阶段。

`/wewo-build` 的唯一职责是：

> 综合当前可用的需求、技术设计、测试场景和现有项目，确定实现约束、测试接缝与纵向切片，通过真实的 TDD 循环逐步完成代码实现，并使用切片级需求审查、代码质量检查和最终验证证据控制代码质量，最终生成实施计划、实施记录以及对应的生产代码和测试代码。
