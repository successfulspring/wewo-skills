# `wewo-test` Skill 需求说明

## 1. Skill 定位

`/wewo-test` 是 `wewo-skills` 中负责**测试路由、自动化测试生成、真实测试执行、人工测试管理和测试结果汇总**的 Skill。

它不是单纯的 Playwright Skill，也不是只负责生成测试代码。

它需要根据测试场景、实际代码、项目已有测试基础和当前运行环境，为每个场景选择最合适的验证方式，包括：

- 单元测试；
- 前端组件测试；
- 集成测试；
- API 自动化测试；
- 契约测试；
- Web E2E 测试；
- 安全行为测试；
- 数据库与迁移测试；
- 必要的性能和可靠性测试；
- 人工测试。

核心职责可以概括为：

```text
收集测试依据
→ 分析实际项目与代码变更
→ 建立待验证场景清单
→ 为每个场景选择测试层级
→ 评估自动化可行性
→ 准备工具、环境和测试数据
→ 生成或补充自动化测试
→ 真实执行测试
→ 分析失败和 Flaky
→ 生成可执行的人工测试清单
→ 汇总所有测试结果
→ 给出测试门禁结论
```

------

## 2. Skill 独立性

`/wewo-test` 可以独立运行，不依赖其他能力已经执行。

可以直接接收：

- 用户描述的测试目标；
- 指定功能或模块；
- 当前工作区代码；
- 指定 Commit、分支或 Diff；
- Issue、Bug 或验收要求；
- API 文档；
- 页面地址；
- 测试账号；
- 现有测试代码；
- 项目启动说明；
- 用户指定的测试环境。

没有可用工件时，仍应根据实际代码、公开接口、页面行为、现有测试和用户要求，建立本次测试所需的最小测试矩阵。

------

## 3. 与测试设计工件的关系

测试设计能力生成以下工件：

```text
test-plan.md
→ 测试范围、风险、策略、环境和退出条件

test-cases.md
→ 测试场景、优先级、步骤、数据和预期结果
```

`/wewo-test` 负责将这些设计转换为真实执行：

```text
测试场景
→ 实际测试层级
→ 测试脚本或人工任务
→ 真实执行结果
→ 缺陷、阻塞和测试结论
```

### 使用强度

当 `test-cases.md` 由用户显式提供或在当前对话上下文中存在时，它是主要场景清单；当 `test-plan.md` 由用户显式提供或在当前对话上下文中存在时，它是可选的范围与策略参考。

两份工件都不是强制依赖。不得自动扫描 `docs/wewo/` 或仓库寻找历史工作流文档；文档存在于工作区本身不构成读取授权。

### 允许调整的内容

`/wewo-test` 可以根据实际情况调整：

- 测试层级；
- 自动化工具；
- 测试接缝；
- 用例拆分与合并；
- E2E 是否改为 API 或集成测试；
- 自动化是否暂时改为人工测试。

不能擅自修改：

- 业务预期；
- 验收标准；
- 权限规则；
- 数据一致性要求；
- 安全要求。

例如：

```text
原建议：Playwright E2E
实际执行：API 集成测试
原因：该场景验证的是服务端幂等性，API 测试更稳定且证据更直接
```

这是允许的。

### 不写回执行结果

不要把以下内容直接混入 `test-plan.md` 或 `test-cases.md`：

- Passed；
- Failed；
- 执行时间；
- 缺陷编号；
- 日志；
- 截图；
- 实际响应。

测试设计和测试执行记录必须分离。

### 必需证据层级的执行义务

对于用户显式提供或在当前对话上下文中存在的 `test-cases.md` 中的每个 P0/P1 场景，应检查：

- 推荐测试层级；
- 必需证据层级；
- 自动化适用性；
- 当前可用的证据。

当场景的必需证据层级为 E2E 时，`/wewo-test` 必须执行以下之一：

- 执行 E2E 并标记为 Passed；
- 执行 E2E 并标记为 Failed；
- 以具体阻塞原因标记为 Blocked；
- 以明确合理的理由标记为 Not Run。

不得用单元、组件、集成或 API 证据静默替代必需的 E2E 证据，并声称该场景已有充分证据。

当 E2E 仅为推荐层级时，如果其他层级能提供等效的直接证据，可以选择其他层级，但必须记录执行层级改变的原因。

```text
示例：
推荐测试层级：E2E
必需证据层级：集成或更高
实际执行：API 集成
原因：目标行为在 HTTP 边界可完整观察和验证，浏览器交互不增加必需的证据。

这是允许的。

但：
必需证据层级：E2E
不能被静默降级。
```

------

## 4. 与已有测试代码的关系

实现阶段可能已经产生测试代码，例如开发过程中的单元测试、必要的集成测试和实现者自检。

`/wewo-test` 负责：

- 复用当前仓库中已有的测试代码；
- 检查已有测试是否真实有效；
- 补充遗漏的自动化测试；
- 执行更完整的回归、API、E2E 和验收测试；
- 管理人工测试；
- 给出独立测试结论。

已有测试优先复用，不应重复生成同类测试。

实现者记录不能代替 `/wewo-test` 本次真实执行的证据。

------

## 5. 产出内容

建议固定生成：

```text
test-execution.md
manual-test-checklist.md
test-artifacts/
```

同时可能新增或修改实际测试资产：

```text
单元测试文件
组件测试文件
集成测试文件
API 测试文件
契约测试文件
E2E 测试文件
Fixture
Mock
测试数据构造工具
Page Object
测试配置
Reporter 配置
```

### `test-execution.md`

记录：

- 实际测试范围；
- 测试场景与真实测试映射；
- 自动化执行结果；
- 人工测试状态；
- 失败归因；
- 缺陷和阻塞；
- 量化指标；
- 测试门禁。

### `manual-test-checklist.md`

记录：

- 不能或不适合自动化的场景；
- 操作步骤；
- 预期结果；
- 证据要求；
- 人工执行状态。

### `test-artifacts/`

可保存：

```text
Playwright HTML 报告
JSON/JUnit 报告
测试日志
覆盖率报告
失败截图
Trace
必要的视频
性能测试结果
结构化执行结果
```

不得在报告和测试产物中泄露真实密码、Token、Cookie、密钥或生产数据。

# 测试范围与路由

## 6. 测试范围确定

优先级建议为：

```text
用户明确指定范围
→ 使用用户指定范围

用户指定功能、Issue 或需求
→ 测试该功能及其必要回归范围

存在明确 Diff
→ 以本次 Diff 及受影响调用链为中心

范围仍不明确
→ 分析当前分支变更，并向用户确认关键边界
```

开始前记录：

- 当前代码版本；
- 分支或 Commit；
- 测试环境；
- 测试目标；
- 测试范围；
- 回归范围；
- 本次不测试的内容；
- 环境限制。

------

## 7. 建立测试场景矩阵

测试执行前应建立统一矩阵：

| 场景         | 优先级 | 风险       | 建议层级 | 实际层级       | 自动化状态 |
| ------------ | ------ | ---------- | -------- | -------------- | ---------- |
| 正常取消订单 | P0     | 核心链路   | E2E      | Playwright E2E | 可自动化   |
| 重复取消订单 | P0     | 幂等       | 集成/API | API 集成       | 可自动化   |
| 越权取消订单 | P0     | 权限       | API      | API 自动化     | 可自动化   |
| 弹窗视觉效果 | P2     | 体验       | 人工     | 人工           | Manual     |
| 库存回滚     | P0     | 数据一致性 | 集成     | 数据库集成     | 可自动化   |

目标不是让全部场景都成为 E2E，而是：

> 使用成本最低、执行最快、结果最稳定、证据最直接的测试层级验证每个场景。

------

## 8. 测试类型路由

### 单元测试

适合：

- 纯函数；
- 业务规则；
- 状态判断；
- 数据转换；
- 输入边界；
- 独立异常分支；
- 算法逻辑。

例如：

```text
订单状态是否允许取消
价格计算
状态转换
字段格式化
```

### 前端组件测试

适合：

- 组件条件渲染；
- 表单校验；
- 按钮状态；
- 弹窗交互；
- 前端错误提示；
- 局部状态变化。

### 集成测试

适合：

- Service 与 Repository；
- 应用服务与真实数据库；
- 事务；
- 缓存；
- 消息队列；
- 文件系统；
- 外部服务适配层。

例如：

```text
订单状态和库存回退是否处于同一事务
异常时是否完整回滚
重复消息是否产生重复副作用
```

### API 自动化测试

适合：

- HTTP 状态码；
- 请求参数；
- 返回 Schema；
- 错误码；
- 身份认证；
- 资源级权限；
- 幂等；
- 服务端业务校验；
- 接口兼容性。

工具应服从项目技术栈，例如：

```text
pytest + httpx
Supertest
REST Assured
Newman
仓库已有 API 测试框架
```

### 契约测试

适合：

- OpenAPI Schema；
- 前后端接口字段；
- 服务间协议；
- 消息格式；
- 序列化兼容；
- 第三方接口适配。

### Web E2E 测试

适合：

- 关键用户旅程；
- 页面与后端整体联通；
- 跨页面操作；
- 浏览器交互；
- 用户可观察结果；
- 关键业务闭环。

Playwright 是 Web E2E 的默认优先候选，但不能无条件用于所有场景。

### 数据库与迁移测试

适合：

- Migration；
- 历史数据兼容；
- 默认值；
- 数据回填；
- 唯一约束；
- 索引；
- 升级和回滚；
- 新旧版本数据转换。

### 安全行为测试

适合验证：

- 未登录访问；
- 越权操作；
- 资源级权限；
- 非法输入；
- 文件类型限制；
- Token 过期；
- 重复请求；
- 跨用户数据；
- 服务端重新校验；
- 状态机绕过。

默认只进行与当前功能相关、可控、非破坏性的安全行为验证。

### 性能与可靠性测试

仅在需求或风险明确时执行：

- 响应时间；
- 批量操作；
- 小规模并发；
- 重复提交；
- 超时；
- 重试；
- 大数据量；
- 长任务；
- 资源泄漏。

正式压力测试需要：

- 独立环境；
- 明确指标；
- 数据容量；
- 用户授权。

### 人工测试

适合：

- 视觉还原；
- 用户体验；
- 文案；
- 真实设备；
- 打印机、扫码枪等硬件；
- 真实短信或电话；
- 验证码；
- 真实支付；
- 第三方不可控页面；
- 需要主观判断的内容；
- 自动化成本远高于长期收益的低频场景。

# 自动化可行性

## 9. 自动化评估

每个测试场景应分类为：

```text
Direct Automation
可以直接自动化

Automation with Setup
补充少量 Fixture、账号或数据后可以自动化

Change Test Level
调整到其他测试层级更合适

Infrastructure Required
需要新增测试基础设施

Blocked
被环境或依赖阻塞

Manual Preferred
人工测试更合适

Not Applicable
场景不再适用

Needs Clarification
业务预期不明确
```

评估因素包括：

- 是否存在稳定入口；
- 是否有可重复测试数据；
- 是否有测试账号；
- 是否依赖验证码；
- 是否依赖真实支付或外部页面；
- 是否会产生不可控副作用；
- 是否能安全清理数据；
- 场景执行频率；
- 自动化长期价值；
- 项目已有测试框架；
- 测试稳定性；
- 自动化维护成本。

------

## 10. 自动化优先级

自动化实施顺序建议为：

```text
项目已有相关测试
→ 直接执行并检查

项目已有测试框架但缺少场景
→ 在现有框架中补充

项目没有该类测试框架
→ 判断是否需要持久接入

只做一次验收
→ 优先临时隔离执行

需要大规模新增测试基础设施
→ 先向用户说明并确认
```

不能为了统一技术栈，擅自替换项目已有的 pytest、Jest、Vitest、Cypress、Playwright 或其他测试体系。

------

# 自动化执行流程

## 11. 通用自动化流程

所有可自动化测试采用统一过程：

```text
确认场景和预期
→ 选择测试层级
→ 检查项目现有测试基础
→ 确认测试接缝
→ 复用已有 Fixture 和辅助能力
→ 生成或修改测试代码
→ 准备测试环境与数据
→ 运行目标单条测试
→ 修正测试脚本问题
→ 执行目标测试集
→ 执行必要回归
→ 收集日志和报告
→ 分析失败和 Flaky
→ 写入执行矩阵
```

生成测试代码不等于测试完成。

只有真实执行并得到符合预期的结果，才能标记为 `Passed`。

------

## 12. Playwright E2E 分支

当场景适合 Web E2E 时，应执行：

```text
检查 package.json 与 Lock 文件
→ 检查已有 E2E 目录和配置
→ 检查 Playwright 是否存在
→ 决定复用、持久接入或临时使用
→ 准备 Chromium 或 Chrome
→ 启动项目或连接测试环境
→ 浏览并理解真实页面
→ 识别稳定 Locator
→ 生成测试脚本
→ 运行单条测试并调试
→ 执行目标测试集
→ 收集 HTML、JSON、截图和 Trace
→ 映射回测试场景
```

### Playwright 测试质量原则

测试应从用户行为出发，并优先使用：

```text
getByRole
getByLabel
getByPlaceholder
getByText
getByTestId
```

CSS 和 XPath 仅作为最后选择。上传的 Playwright Skill 也将语义化 Locator、自动等待、测试隔离和可读性列为核心原则。

禁止默认生成：

- `waitForTimeout()`；
- 依赖执行顺序的测试；
- 多个测试共享可变业务数据；
- 脆弱的层级 CSS Selector；
- 只验证 DOM 内部实现的断言；
- 不清理副作用的测试。

附件同样明确将硬编码等待、共享可变状态、脆弱 Selector 和不清理测试数据列为反模式。

### Page Object 使用规则

不能强制所有项目使用 Page Object。

```text
项目已有 POM
→ 沿用

存在大量重复页面交互
→ 使用 POM 或组件对象

只有少量简单场景
→ 允许直接在 Spec 中表达用户行为
```

### 浏览器策略

默认：

```text
Playwright 自带 Chromium
```

仅在明确要求时使用：

- 系统 Google Chrome；
- Firefox；
- WebKit；
- 移动设备模拟。

不能默认安装和运行所有浏览器。

### 报告与调试产物

Playwright 配置应根据项目需要生成：

- HTML Reporter；
- JSON 或 JUnit；
- 失败截图；
- Trace；
- 必要的视频。

附件中的参考配置也包含 HTML、JSON 报告，以及失败截图、Trace 和视频策略。

------

# 工具发现与安装

## 13. 工具发现

不能假设 Agent 环境中一定存在所需测试工具。

应检查：

- 项目依赖文件；
- Lock 文件；
- 测试配置；
- 测试目录；
- 项目脚本；
- CI 配置；
- 当前环境中的可执行程序；
- 浏览器和运行时版本。

例如检查 Playwright 时，应先读取项目文件，不要仅为了检测而执行可能触发下载的命令。

------

## 14. 工具安装策略

### 项目已经声明工具

使用项目现有包管理方式恢复依赖：

```text
npm ci
pnpm install --frozen-lockfile
uv sync
项目已有构建命令
```

不得擅自升级版本或更换包管理器。

### 项目没有工具，但测试资产需要长期保留

例如正式引入 Playwright，可能修改：

- `package.json`；
- Lock 文件；
- Playwright 配置；
- E2E 目录；
- 测试脚本；
- `.gitignore`；
- CI。

执行前必须说明改动并获得用户确认。

### 一次性测试

优先：

- 临时目录；
- 隔离环境；
- 固定工具版本；
- 不修改项目依赖；
- 执行完成后清理工具环境。

### 必须确认的安装

包括：

- 系统级依赖；
- 管理员权限；
- Docker；
- 大体积浏览器安装；
- 系统 Chrome；
- 启动持久服务；
- 修改 Lock 文件；
- 修改 CI；
- 访问外部云测试服务；
- 上传源码或测试数据。

### 禁止默认执行

- `curl | sh`；
- 不明来源二进制；
- 关闭 TLS 校验；
- 使用生产密钥；
- 污染系统全局环境；
- 自动上传公司代码；
- 在生产环境运行破坏性测试。

工具安装失败不代表所有测试停止。

应继续执行仍然可用的测试，并记录：

- 安装失败原因；
- 未执行测试；
- 降级验证；
- 剩余风险。

# 测试环境与数据安全

## 19. 环境确认

具有写入行为的测试执行前，必须确认：

- 当前 URL；
- 当前环境类型；
- 是否为本地、测试或 Staging；
- 测试账号；
- 数据是否可删除；
- 是否会发真实邮件或短信；
- 是否会产生真实支付；
- 是否会调用真实第三方；
- 是否会修改共享库存；
- 是否允许批量和并发执行。

默认禁止在生产环境执行写入型自动化测试。

### 19.1 生产类证据与开发模式证据

不要求每次测试运行都虚构或创建生产类环境。

只有以下情形之一确立生产类证据相关时，才需要生产类证据：

- 目标部署 / 启动模式；
- 验收环境；
- 项目约定；
- 用户测试目标。

当生产类证据相关时：

1. 记录实际测试的环境 / 模式。
2. 开发模式下获得的证据只证明该开发模式下观察到的行为。
3. 成功的开发模式测试不得被表述为以下内容的证据：
   - 生产类覆盖；
   - 生产就绪；
   - 部署模式下行为成功。
4. 如果尝试生产类执行，但环境、工具或运行时问题阻止了执行：
   将生产类环境检查记录为 Blocked，并记录具体阻塞原因。
5. 如果生产类验证相关但有意未尝试：
   将其记录为 Not Run，并说明原因。
6. 开发模式回退可以提供补充的行为证据，但不能替代缺失的生产类证据。
7. 场景执行状态与环境覆盖情况必须保持分离。

示例：

场景：
- 在开发模式下 Passed。

环境证据：
- 开发模式：Verified。
- 生产类模式：Blocked —— 静态资源加载失败。

报告不得将其压缩为：

"该场景已在生产环境完全验证。"

除非现有状态模型需要，否则不要引入新的全局场景状态；在适当的地方复用现有的 Passed / Failed / Blocked / Not Run 语义，并显式描述未验证的环境覆盖。

------

## 20. 测试数据

每个自动化测试应尽量做到：

```text
创建唯一测试数据
→ 执行测试
→ 验证结果
→ 清理测试数据
```

测试之间不得依赖执行顺序。

共享账号或共享业务数据无法隔离时：

- 降低并行度；
- 使用唯一标识；
- 串行执行相关测试；
- 明确数据清理方式；
- 记录残留风险。

认证状态文件、Cookie、Token 等必须：

- 使用测试账号；
- 不提交到版本库；
- 不输出到公开报告；
- 执行后按策略清理。

# 结果状态与失败归因

## 22. 自动化测试状态

统一使用：

```text
Passed
真实执行并通过

Failed
真实执行且不符合预期

Blocked
环境、账号、数据或依赖导致无法执行

Skipped
根据明确规则跳过

Not Run
尚未执行

Flaky
相同代码和环境下结果不稳定

Not Applicable
场景已经不适用
```

测试脚本已生成但未执行，应标记为：

```text
Not Run
```

而不是 `Passed`。

------

## 23. 失败归因

每个失败必须分类为：

```text
Product Defect
生产代码缺陷

Test Defect
测试脚本、Fixture 或断言问题

Test Data Issue
测试数据准备或清理问题

Environment Blocker
服务、数据库、网络、浏览器或账号问题

Existing Failure
本次变更前已经存在

Flaky
结果不稳定

Requirement Conflict
需求、用例和代码预期冲突

Unverified
证据不足，无法确认
```

只有确认属于产品实现的问题，才能写入正式产品缺陷清单。

------

## 24. 重试与 Flaky

不得通过无限重试让测试“变绿”。重试不得用于掩盖 Flaky 行为。

当某个测试出现过以下任一情况时：

- 通过与失败的混合结果；
- 无法解释的间歇性失败；
- 失败需要通过改变同步、等待、时序或测试装置行为才得以解决；

适用以下证据规则：

1. 仅一次成功的重跑不能证明该测试稳定。
2. 在声称受影响测试稳定、或修正后未观察到 Flaky 行为之前，应在代码不变、环境基本不变的条件下，对最终的受影响测试范围进行重复执行。
3. 受影响测试的默认最低重复证据为 3 次连续执行。这不要求整套测试总是运行三遍；只有当对曾出现不稳定、或需要时序或同步修正的测试或路径作出稳定性结论时才适用。
4. 如果这些重复执行仍包含通过与失败的混合结果，应将受影响测试标记为 Flaky。
5. 如果未收集到足够的重复证据，不得声称“无 Flaky 测试”“稳定”或作出等效的类别化稳定性结论，而应报告稳定性尚未被充分确立。
6. 作出稳定性结论时，应记录重复次数和观察到的结果。

优先使用证据范围明确的表述，例如：

```text
在记录的环境下，受影响测试连续 3 次执行中未观察到 Flaky 行为。
```

而不是缺乏证据支持的类别化表述，例如：

```text
没有 Flaky 测试。
```

首次失败应先收集日志、截图、Trace 和环境证据；怀疑测试脚本问题时修复脚本后重新执行；怀疑偶发问题时在代码和环境不变的情况下进行有限复跑。Playwright 配置中的自动重试只能作为诊断辅助，不能掩盖真实 Flaky。

# 测试门禁

## 29. 测试结论

最终结论分为：

```text
通过
条件通过
不通过
未完成 / 无法确认
```

### 通过

要求：

- P0 场景全部完成并通过；
- 必要的 P1 场景完成；
- 核心用户链路通过；
- 关键权限、事务和数据一致性测试通过；
- 没有阻塞发布的产品缺陷；
- 必要人工测试完成；
- 没有未接受的高风险 Blocked 或 Flaky。

### 条件通过

满足：

- 核心链路已经通过；
- 没有阻塞性缺陷；
- 剩余问题风险较低；
- 未完成项和剩余风险明确；
- 有风险接受人和后续计划。

### 不通过

存在以下任一情况：

- P0/P1 核心场景失败；
- 权限测试失败；
- 事务或数据一致性测试失败；
- 核心 E2E 流程失败；
- 数据迁移失败；
- 存在阻塞性产品缺陷；
- 自动化测试产生不可控副作用；
- 测试误连接生产环境。

### 未完成 / 无法确认

包括：

- 测试环境不可用；
- 缺少关键账号或数据；
- 关键人工测试尚未完成；
- 高风险场景被阻塞；
- 测试结果持续 Flaky；
- 关键外部系统无法验证；
- 必要工具无法运行。

即使无法给出最终结论，也应输出已执行测试、已发现问题和剩余风险。

# 核心硬规则

## 33. `/wewo-test` 必须遵守

```text
1. /wewo-test 是测试执行编排 Skill，不是单一 Playwright Skill。

2. 每个场景都必须选择最合适的测试层级，而不是全部转成 E2E。

3. test-cases.md 是可选场景清单，仅在用户显式提供或在当前对话上下文中存在时使用。

4. 可以调整测试层级和执行方式，不能擅自修改业务预期。

5. 优先复用项目已有测试框架、配置、Fixture 和命令。

6. 只有真实执行后的测试才能标记为 Passed。

7. 测试代码生成完成但未执行，必须标记为 Not Run。

8. 自动化失败必须区分产品缺陷、测试缺陷、数据问题和环境阻塞。

9. 不得通过弱化断言、跳过场景或无限重试让测试变绿。

10. Flaky 必须被明确记录，不能被重试掩盖。

11. 可以修改测试代码和已确认范围内的测试配置。

12. 新增依赖、修改 Lock 文件、CI 或大型测试基础设施必须先获得用户确认。

13. 默认不得修改生产代码。

14. 需要生产代码可测试性改造时，应生成 Testability Change Request，并交由独立的实现能力完成。

15. 自动化测试默认不得对生产环境执行写操作。

16. 测试数据必须尽量隔离、可识别并可清理。

17. 不能自动化的场景必须生成可执行的人工测试清单。

18. 没有人工执行证据时，不能将人工测试标记为通过。

19. 工具缺失时可以受控安装，但安装失败不能伪装成测试通过。

20. Playwright E2E 默认优先使用项目已有配置和 Chromium。

21. 不得强制所有项目使用 Page Object、全部浏览器或固定目录结构。

22. 测试工具输出、HTML 报告和覆盖率必须来自本次真实执行。

23. 测试结论必须基于最新代码版本、真实环境和实际执行证据。

24. 测试通过率和自动化率不能单独决定是否允许发布。

25. 核心权限、事务、数据一致性和 P0 业务链路失败必须阻止通过。
```

# Skill 最终职责

`/wewo-test` 的最终职责可以概括为：

> 基于当前可用的需求、测试计划、测试用例、实际代码变更和项目已有测试体系，建立统一的测试执行矩阵，为每个场景选择最合适的单元、组件、集成、API、契约、E2E、安全、数据、性能或人工验证方式；优先复用已有测试，受控地生成和执行缺失的自动化测试，管理测试工具、浏览器、环境和数据副作用，对失败进行产品、测试、环境和 Flaky 归因，为无法自动化的场景生成可执行人工测试任务，最终输出真实、可追踪、可量化并具有明确测试门禁的测试执行报告。
